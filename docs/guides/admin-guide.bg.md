## 1. От какво се състои

| Част | Какво прави | Как се пуска |
|---|---|---|
| Приложението (Next.js) | Сайтът на <http://localhost:3000> | `pnpm dev` (разработка) или `pnpm build` и `pnpm start` |
| Worker-ът | Фоновите задачи: изпраща писмата, пуска задачите по график | `pnpm worker:dev` или `pnpm worker` |
| PostgreSQL 18 + PostGIS 3.6 | Базата данни | Docker Compose |
| Mailpit | Пощенска кутия за проба: всички писма остават тук | Docker Compose, <http://localhost:8025> |
| SeaweedFS | Хранилище за файлове (S3), за доказателствата от следващите етапи | Docker Compose, <http://localhost:8333> |

Услугите слушат само на `127.0.0.1`: не са достъпни от други компютри в мрежата.

## 2. Пускане локално на Windows (Docker Desktop и WSL2)

### Изисквания

- Windows 10 или 11 с WSL2 и дистрибуция **Ubuntu 24.04** (`wsl --install -d Ubuntu-24.04`).
- [Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/) с WSL2 backend. В *Settings → Resources → WSL integration* включете дистрибуцията Ubuntu; дайте на Docker около 8 GB памет.
- Хранилището е **във файловата система на WSL2** (например `~/src/wingchunroots`), не под `C:\` или `/mnt/c`: там `pnpm install` и `next build` са многократно по-бързи, а правата на файловете са верни. Всички команди се пускат от терминала на WSL2, никога от PowerShell или cmd. Това е основният път; за компютър без WSL2 има втори, по-бавен (виж „Windows без WSL2 (Git Bash)“ по-долу).

### Първо пускане

1. Инструментите (в терминала на Ubuntu):

   ```bash
   sudo apt-get update && sudo apt-get install -y git postgresql-client
   curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash   # после отворете терминала наново
   nvm install          # чете .nvmrc (26.12.1)
   npm install --global pnpm@12.14.0
   ```

2. Хранилището, настройките и услугите:

   ```bash
   mkdir -p ~/src && cd ~/src
   git clone https://github.com/VladimirKadanov/wingchunroots.git
   cd wingchunroots
   nvm use                        # Node от .nvmrc
   scripts/init-env.sh            # .env с местни пароли, ключове и тестови акаунти (само за тази машина)
   docker compose up -d --wait    # PostgreSQL + PostGIS, Mailpit, SeaweedFS
   scripts/db-bootstrap.sh        # роли и собственик на базата, веднъж за база
   pnpm install
   pnpm db:migrate && pnpm db:seed   # схема и измислени демо данни
   pnpm exec playwright install --with-deps chromium   # браузър за E2E тестовете на вашата машина
   ```

3. Пускане (два терминала):

   ```bash
   pnpm dev          # сайтът: http://localhost:3000
   pnpm worker:dev   # във втори терминал: фонови задачи и поща
   ```

4. Проверка: `scripts/verify.sh M02`; последният ред трябва да е `VERIFY M02: PASS`.

Файлът `.env` не се качва в Git. Ако е създаден преди M01, M01b или M02, пуснете `scripts/init-env.sh` още веднъж: той пази съществуващите стойности и само добавя липсващите (паролите на трите роли в базата, `MAIL_TRANSPORT=smtp`, а от M02 настройките на акаунтите, виж раздел 6). След нови пароли на ролите пуснете `scripts/db-bootstrap.sh`.

### Пускане като в production (по желание)

```bash
pnpm build
pnpm start      # http://localhost:3000
pnpm worker     # във втори терминал
```

### Windows без WSL2 (Git Bash)

Втори, по-бавен път за компютър, на който няма WSL2. Основният път остава WSL2 по-горе (план §7.6, [ADR 0001](../adr/0001-stack.md)); този е проверен със `scripts/verify.sh M04`. Хранилището е на диск на Windows (например `D:\work\wingchunroots`), а всички команди се пускат от **Git Bash** (идва с Git for Windows), никога от PowerShell или cmd. Услугите пак са в Docker Desktop. `pnpm install`, `next build` и E2E тестовете са по-бавни, отколкото в WSL2, затова E2E върви с по-малко паралелни процеси.

Разлики от стъпките по-горе:

- **Node 26.12.1** с [nvm for Windows](https://github.com/coreybutler/nvm-windows): `nvm install 26.12.1` и `nvm use 26.12.1`. Ако nvm отговори „not yet released or available“ (или търси `-arm64.msi` на компютър с x64), разархивирайте `node-v26.12.1-win-x64.zip` (`win-arm64` на компютър с ARM) от <https://nodejs.org/dist/v26.12.1/> в `<nvm root>\v26.12.1` (`nvm root` показва папката), после `nvm use 26.12.1` и инсталирайте pnpm наново. На nvm for Windows давайте версията изрично, вместо `nvm use` от `.nvmrc`.
- **pnpm** с `npm install --global --allow-scripts=pnpm pnpm@12.14.0`, никога през Corepack (npm на Node 26 по подразбиране не пуска инсталационните скриптове, а на Windows скриптът на pnpm създава командата `pnpm`). `npm config get prefix` трябва да е папката на активния Node (`C:\Program Files\nodejs` при nvm for Windows); prefix, оставен от по-стар мениджър на версии като Nodist, слага pnpm извън `PATH` (`npm config set prefix "C:\Program Files\nodejs" --location=user`). Проверете с `pnpm -v`. Грешка `Cannot find module …\corepack\pnpm\…` значи, че по `PATH` първи е стар shim на Corepack (`pnpm`, `pnpm.cmd` в `%AppData%\npm`); тогава инсталирайте pnpm в папката на активния Node, която nvm слага по-напред в `PATH`: `npm install --global --allow-scripts=pnpm --prefix "$(dirname "$(which node)")" pnpm@12.14.0` (`which`, а не `command -v`, който показва псевдоним като `winpty node.exe`).
- **psql 15 или по-нов в `PATH`** вместо `postgresql-client` от apt, например клиентът от [PostgreSQL for Windows](https://www.postgresql.org/download/windows/). В `~/.bashrc`: `export PATH="/c/Program Files/PostgreSQL/17/bin:$PATH"`.
- **Порт 5432 е зает** от PostgreSQL, инсталиран направо в Windows (`docker compose up` казва `bind: An attempt was made to access a socket in a way forbidden by its access permissions`): след `scripts/init-env.sh` задайте `POSTGRES_PORT=5433` в `.env` и сменете порта в `DATABASE_URL` и `TEST_DATABASE_URL` на `5433`, преди първото `docker compose up -d --wait`.
- **Браузърът за E2E:** `pnpm exec playwright install chromium` (без `--with-deps`, което е само за Linux).
- **Паралелни E2E процеси:** `PW_WORKERS=2` в `.env` (виж `.env.example`). `scripts/verify.sh` го чете от `.env`, а обикновеното `pnpm e2e` чете само средата: добавете `export PW_WORKERS=2` в `~/.bashrc` или пуснете `PW_WORKERS=2 pnpm e2e`. Измерено на компютър с 8 ядра и Docker Desktop, `scripts/verify.sh M04` (148 E2E теста): с 1 процес минава за 7,4 min, с 2 — за 4,5–5,0 min, а с 4 (подразбиращото се на Playwright) пада тестът за 404 на скрита личност: при това натоварване проверката на личността в proxy минава срока си от 500 ms и страницата отговаря сама със статус 200 (раздел 11). Ако едновременно върви друга тежка работа, и 2 процеса могат да изпуснат този срок или `statement_timeout` от 2 s; тогава ползвайте 1.
- **Краищата на редовете** остават LF (`.gitattributes`), каквото и да казва `core.autocrlf`.

При обновяване (раздел 4) влезте в папката на хранилището на диска на Windows вместо `~/src/wingchunroots` и дайте на `nvm use` версията от `.nvmrc` (например `nvm use 26.12.1`).

## 3. Спиране

За спиране на всичко, без да губите данни, са достатъчни първите две стъпки.

- **Сайтът и worker-ът:** `Ctrl+C` в терминала им. Worker-ът спира плавно при `SIGTERM` (и при `Ctrl+C`): довършва текущата задача и затваря връзките.
- **Услугите в Docker:** `docker compose down`. Данните остават в именуваните томове на Docker и се връщат при следващото `docker compose up -d --wait`.
- **Изтриване на всички местни данни** (базата, писмата, файловете): `docker compose down -v`. Това е необратимо; след него повторете стъпките от „Първо пускане“ от `docker compose up -d --wait` нататък.
- **Само данните в базата, без услугите:** `pnpm db:reset`, после `pnpm db:migrate && pnpm db:seed`. Работи само с местна база или с `TEST_DATABASE_URL`, никога с `NODE_ENV=production`.

За обновяване, след като собственикът е слял нов етап в `main`:

```bash

После пуснете сайта и worker-а наново (раздел 2, стъпка 3). Какво е ново за потребителя, пише в [`user-guide.bg.md`](user-guide.bg.md).

## 5. Worker и поща (M01b)

- **Worker-ът е отделен процес:** `pnpm worker` (или `pnpm worker:dev`, който се рестартира при промяна в кода). Свързва се с базата само като ролята `app_rw`, без право да създава таблици или схеми. Спира плавно при `SIGTERM`.
- **Всички писма минават през worker-а:** приложението ги записва в опашката в същата транзакция като промяната, която ги поражда, а worker-ът ги изпраща. Във Фаза 1 нищо не излиза извън компютъра.
- **`MAIL_TRANSPORT=smtp`** (това записва `scripts/init-env.sh`): писмата отиват в Mailpit. Пуснете го с `docker compose up -d --wait mailpit` и ги четете на <http://localhost:8025>. `SMTP_URL` може да сочи само към местния Mailpit (`localhost`, адрес на loopback или `mailpit`); всеки друг хост спира worker-а още при старта.
- **`MAIL_TRANSPORT=file`** (когато променливата липсва; облачните сесии): всяко писмо се записва в папката `.mail/` като `.eml` и `.json`.
- **Пробно писмо:** `pnpm mail:check <адрес>`, например `pnpm mail:check demo@wingchunroots.test`, докато worker-ът работи. Писмото се появява в Mailpit (или в `.mail/`).
- **Почистване по график:** задачата `retention.purge` върви всеки ден в 03:17 UTC. Адресите в `email_delivery` се изтриват 90 дни след като писмото е записано, освен в писмата с покана; адресът в поканите, заедно с копието му в записа за писмото с поканата, се изтрива 30 дни след края на поканата (приета, изтекла или оттеглена). От M02 задачата трие и изтеклите сесии, изтеклите токени за потвърждаване и нова парола, изтеклите броячи на входа и акаунтите, непотвърдени 7 дни след регистрацията.

- **Ключове за търсене (M07):** задачата `search.keys.rebuild` пише ключовете за търсене на всички хора. `pnpm db:seed` я поставя в опашката, затова след зареждане на демо данните търсенето работи, щом worker-ът тръгне. Виж раздел 13.
- **Преизчисляване на линиите (M09):** след всяко одобрение на заявка към учител приложението поставя в опашката задачата `lineage.recompute`. Worker-ът преизчислява членовете на засегнатите линии (`lineage_membership`, само от публичните връзки) и после вика уеб процеса на `POST /api/internal/revalidate` с тага на тези данни (`lineage-membership:<id>`). Кешът на профилите и линиите изчиства самото одобрение веднага, затова worker-ът не го праща повторно. Задачата има свой лимит от 30 s на заявка към базата (не 2 s като уеб заявките) и праща обновяването на кеша и когато преизчисляването се провали, преди pg-boss да опита отново. Виж раздел 14.

Останалите настройки (`SMTP_URL`, `MAIL_FILE_DIR`, `MAIL_FROM`, `MAILPIT_URL`) са описани в `.env.example`.

## 6. Акаунти, първият администратор и TOTP (M02)

### Настройки в `.env`

`scripts/init-env.sh` ги създава. При по-стар `.env` ги добавя, без да пипа останалото.

| Настройка | Какво е |
|---|---|
| `APP_URL` | Адресът, на който отваряте сайта (по подразбиране `http://localhost:3000`). С него започват връзките в писмата, а заявките към `/api/*`, които променят нещо, се приемат само от него. Ако отваряте сайта на друг адрес или порт, сменете го и пуснете сайта и worker-а наново |
| `BETTER_AUTH_SECRET` | Подписва бисквитките на сесиите и шифрира TOTP тайните. **Не го сменяйте:** смяната изписва всички, а пазените TOTP тайни стават нечетими и персоналът трябва да включи 2FA отново |
| `IP_HMAC_KEY` | Ключът на `ip_hmac` (одитът и сесиите пазят ключов хеш на IP адреса, никога самия адрес). Сменя се веднъж годишно, когато има хостинг |
| `MAIL_SEAL_KEY` | Шифрира токените в писмата за акаунта, докато чакат в опашката на worker-а (поне 32 знака). Задължителен. При смяна писмата, които още чакат, не тръгват и хората искат нова връзка |
| `TRUSTED_PROXIES` | Адресите (или CIDR диапазоните) на обратните проксита пред сайта. Локално остава празен. Нужен е при публикуване: без него сайтът в production не тръгва зад публичен адрес. `next start` излиза веднага с код 1 и съобщение коя настройка липсва или е грешна, така че програмата, която държи сайта пуснат, вижда отказа. Същото важи за запис, който не е IP адрес или CIDR диапазон, за `APP_URL` и за трите тайни |
| `E2E_PASSWORD`, `E2E_TOTP_SECRET` | Паролата на демо акаунтите и TOTP тайната на демо персонала (виж по-долу). **Само за тази машина и за CI.** Никога не се ползват извън тях |

Стойностите са случайни, генерирани за вашата машина, и не се качват в Git. Сайтът, worker-ът, `pnpm db:seed` и тестовете трябва да виждат едни и същи стойности.

### Първият администратор

Администраторът се създава от акаунт, който вече съществува и има включен TOTP. Командата не създава пароли и не отпечатва тайни.

1. Пуснете сайта и worker-а (раздел 2, стъпка 3) и Mailpit.
2. На <http://localhost:3000/sign-up> регистрирайте своя акаунт (виж ръководството за потребителя).
3. В Mailpit (<http://localhost:8025>) отворете писмото **Confirm your e-mail address for WingChunRoots**, натиснете **Confirm e-mail address**, после **Confirm my address**.
4. Влезте. Попълнете профила, ако искате (не е задължително за администратора).
5. Отворете **Me** → **Security settings** (`/account/security`) и включете двуфакторното удостоверяване:
   1. въведете паролата си и натиснете **Set up two-factor authentication**;
   2. сканирайте QR кода с приложението за удостоверяване (или въведете ключа под него);
   3. въведете кода от приложението и натиснете **Turn on two-factor authentication**;
   4. запазете десетте резервни кода (**Copy all codes** или **Download as a text file**), отметнете **I have saved these codes somewhere safe.** и натиснете **Done**.

   Ключът и кодовете се показват само в този браузър, 30 минути. Ако презаредите страницата или минете към приложението и обратно, те са още там.
6. В терминала, в папката на хранилището:

   ```bash
   pnpm admin:create --email вашият@адрес
   ```

   При успех командата пише `admin:create: the account is now an admin (role.change is in the audit log).` Всички сесии на акаунта приключват.
7. Влезте отново с паролата и кода от приложението и отворете <http://localhost:3000/admin>.

Командата отказва и казва защо, без промяна:

- няма акаунт с този адрес;
- адресът не е потвърден;
- TOTP не е включен;
- `NODE_ENV=production`;
- базата не е на тази машина (`DATABASE_URL` не сочи към `localhost`).

Повторно пускане за акаунт, който вече е администратор, не променя нищо. Ролята се записва в одита като `role.change` с причина `pnpm admin:create (local environment)`.

В M02 няма екран за смяна на роли. Ролите `moderator` и `archivist` се дават през API процедурата `admin.setRole`. Може само администратор, чиято сесия е минала втория фактор, и само на акаунт с включен 2FA. Екранът идва с инструментите за преглед в следващите етапи.

### Задължителният TOTP за персонала

Модераторите, архивистите и администраторите са **персонал**. За тях важат правила, които базата и сървърът спазват сами:

- **Роля на персонала** се дава само на акаунт с включен TOTP. Базата отказва такава роля без 2FA, по който и път да дойде.
- **Втори фактор във всяка сесия.** Страниците и действията на персонала, засега `/admin`, искат сесия, която е минала втория фактор. Само включен 2FA не стига. Сесия без проверка се пренасочва към `/account/security?next=/admin`, за да се въведе код.
- **Без „запомнено устройство“.** Персоналът въвежда код при всеки вход.
- **2FA не може да се изключи**, докато акаунтът е персонал.
- **Край на сесиите.** При смяна на ролята и при включване на 2FA всички сесии на акаунта приключват, и в браузъра, и с токен (`Authorization: Bearer`).

Ако администратор загуби телефона си, влиза с резервен код. В M02 сайтът няма друг път за възстановяване на втория фактор, затова резервните кодове се пазят на сигурно място.

### Писмата за акаунта

Писмата на M02 минават през worker-а като всички други. Локално идват в Mailpit (<http://localhost:8025>), а с `MAIL_TRANSPORT=file` (облачните сесии) — в `.mail/`:

- **Confirm your e-mail address for WingChunRoots** — при регистрация и при опит за вход с непотвърден адрес. Връзката води към `/verify-email` и важи 24 часа;
- **Reset your WingChunRoots password** — при **Forgot your password?**. Връзката води към `/reset-password` и важи един час;
- писмо „довършете регистрацията“ — когато някой се регистрира с адреса на акаунт, който още не е потвърден, с **друга** парола. Паролата на този акаунт се изтрива, а връзката в писмото (1 час) задава нова. Така паролата избира само този, който чете пощата. Повторна регистрация със **същата** парола (двойно натискане, писмо, което се бави) не трие нищо и праща нова връзка за потвърждаване;
- писмо „вече имате акаунт“ — когато някой се регистрира с адреса на потвърден акаунт. Нищо в акаунта не се променя; писмото предлага вход или нова парола.

Екранът след регистрация е един и същ във всички случаи, така че никой не научава дали адресът вече има акаунт. Токените в писмата се пазят в опашката шифрирани (`MAIL_SEAL_KEY`). Един акаунт получава на час най-много по 3 писма от всеки вид с връзка (потвърждаване, нова парола, довършване на регистрацията) и 1 писмо „вече имате акаунт“; следващите отпадат тихо. Видовете се броят поотделно, затова чужди регистрации с адреса не могат да изразходват писмата за нова парола, а когато границата е достигната, в пощата вече има връзка, която работи.

Ако писмото не идва, проверете дали worker-ът работи и дали `APP_URL` е адресът, на който отваряте сайта. Броят на неуспешните доставки се вижда на `/admin` (**Failed e-mail deliveries**).

Акаунт, чийто адрес не е потвърден 7 дни след регистрацията, се изтрива от ежедневното почистване заедно със записите за съгласие.

  ```bash
  E2E_TOTP_SECRET="$(grep '^E2E_TOTP_SECRET=' .env | cut -d= -f2-)" pnpm exec tsx -e \

  ```

  Добавете отпечатания ключ в приложението ръчно („въведи ключ“, по време, 6 цифри). Не въвеждайте самата стойност от `.env`: с нея кодовете няма да съвпадат.

Всички акаунти и имена са измислени (`example.test` е резервиран домейн за тестове).

### Ограничения на честотата

Сайтът ограничава опитите от един клиентски адрес:

- вход, регистрация и кодове за втори фактор: 3 за 10 секунди;
- искане на нова парола и ново писмо за потвърждение: 3 в минута.

Тези броячи са в паметта на сайта и се нулират при рестарт. По-важните граници са в базата и не зависят от клиентския адрес:

- **10 поредни неуспешни входа** с един имейл адрес заключват входа с този адрес за 15 минути за браузърите, които не са влизали с него. Правилната парола след това нулира брояча. Опитът се брои, преди паролата да бъде проверена, затова много едновременни опити не получават повече проверки. Грешна парола в настройките за сигурност (2FA, смяна на паролата) се брои в същия брояч;
- **познатите браузъри** — тези, които вече са влизали с правилната парола или са сменили паролата през писмото — имат свой брояч от 10 и чуждото заключване не ги спира (бисквитката `wcr.known_device`, 180 дни). Затова никой не може да държи собственика вън: заключеният собственик на нов браузър иска нова парола, и браузърът става познат. Новата парола прекратява всички познати браузъри на акаунта освен този, от който е зададена;
- опит, който завърши с грешка на сайта (например бавна база), се връща и не се брои;
- **10 поредни грешни кода** — при вход или в сесия, която още не е минала втория фактор — заключват втория фактор на акаунта за 15 минути, и за входа от друг браузър, и за резервните кодове. Сесия, която вече е минала втория фактор, не може да праща кодове, затова откраднатата бисквитка без паролата не заключва собственика. Ако подозирате, че някой знае паролата, нова парола прекратява всички сесии;
- **отказаният вход** и приетите регистрация и искане на нова парола отговарят най-рано след половин секунда (регистрацията — след 0,8 s), за да не издава времето кои адреси имат акаунт. Правилната парола на непотвърден акаунт получава същия отказ като грешната, а сайтът тихо праща нова връзка за потвърждаване;
- **кодът от приложението** важи само веднъж: същият код не се приема втори път;
- **писмата на час** за акаунта: до 3 от всеки вид с връзка и 1 „вече имате акаунт“ (по-горе);
- **смяна на вида акаунт** (Student ↔ Sifu, M08): до 5 за 24 часа на акаунт; **заявки за пилотен достъп**: до 3 за 30 дни на акаунт.

Ако някой е заключен, изчакайте 15 минути или го насочете към **Forgot your password?**: новата парола отключва адреса и браузъра, от който е зададена. Няма команда за ръчно отключване.

Във Фаза 1 сайтът е само локален и приема клиентския адрес от заглавка `X-Forwarded-For` само с един запис. Преди публикуване зад прокси задайте `TRUSTED_PROXIES` ([ADR 0004](../adr/0004-auth.md), раздел 7).

- **Токените** (цветове, шрифтове, размери, радиуси, движение) са само в `src/design/tokens.ts`. След промяна там: `pnpm tokens:build`, който обновява `src/design/generated/tokens.css` и `tokens.json`. Тестовете падат, ако генерираните файлове не са обновени или ако някой цвят няма нужния контраст.

### Страниците на личност и „Not on the record“

Липсваща личност, скрита личност и неправилен адрес дават една и съща страница „Not on the record“, с еднакъв HTML и `noindex, nofollow`, със статус 404. API-то (`/api/v1/people/<адрес>`) също отговаря с 404. Проверка на ръка срещу работещ сървър: `curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/people/demo-claim-only-teacher` и `curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/api/v1/people/demo-claim-only-teacher` дават `404`, а `curl -s http://localhost:3000/people/demo-claim-only-teacher | grep -c 'No public profile at this address'` намира думите в HTML.

Статусът идва от `src/proxy.ts` (решение на собственика от 19.10.2026, [`docs/adr/0008-person-pages-404.md`](../adr/0008-person-pages-404.md)):

- **Кога върви.** Само за `/people/<адрес>` и `/people/<адрес>/lineage`. Никога за `/api/...`, `/healthz` или статичните файлове под `/_next/...`, затова качването на файлове и API-то не минават през него. Собствената форма на Next.js за данните на същите два пътя (`/_next/data/<сборка>/people/<адрес>.json`) минава през него със същата проверка. Проверката на M02 (`scripts/verify.sh M02`) пада, ако се появи `middleware` файл, друг proxy или друг matcher.
- **Какво прави.** Пита услугата за родословието дали посетителят може да види личността: една бърза заявка към базата по индекса, а за непубличен адрес с влязъл потребител и четене на сесията. Ако не може, показва страницата 404 „Not on the record“; адресът в браузъра остава същият.
- **Срокът.** Проверката има 500 ms. Заявките ѝ към базата спират там (`statement_timeout`), а proxy спира да чака след същото време. Бавна или недостъпна база така задържа страницата най-много половин секунда в proxy; после страницата отговаря сама, както без proxy: „Not on the record“ (статус 200, без индексиране) или съобщението си за грешка с Retry. Провалена проверка никога не скрива страница на видима личност.
- **Колко чака страницата.** Всяка процедура за родословието има 2 s за всичко, включително четенето от кеша, когато кешът е празен. Страницата чете на два етапа: първо профила, после разделите (учители, ученици, пътища, наследници) едновременно. При бавна база посетителят вижда състоянието на грешка след най-много около 4,5 s (0,5 s в proxy, 2 s за профила, 2 s за разделите).
- **Дневникът.** При провал или изтекъл срок сървърът записва един ред само с кода на грешката: `[proxy] the person check failed (timeout); the page answers for itself` или например `(57014)` (прекъсната заявка в PostgreSQL). Адресът, сесията и заявката никога не са в дневника. Отделни такива редове с `timeout` или `57014` при натоварване не са проблем; ред с друг код (например име на грешка) означава, че проверката се проваля, и E2E проверката на M04 пада на него. Ако редовете се появяват постоянно, базата е бавна или недостъпна. Проверете:
  - дали базата отговаря: `pg_isready -d "$DATABASE_URL"` и `psql "$DATABASE_URL" -c 'SELECT 1'`;
  - дали има дълги или блокирани заявки: `psql "$DATABASE_URL" -c "SELECT pid, state, wait_event_type, wait_event, now() - query_start AS running FROM pg_stat_activity WHERE state <> 'idle' ORDER BY running DESC NULLS LAST LIMIT 20"` (заявки, които чакат заключване, имат `wait_event_type = Lock`);
  - дневника на PostgreSQL (в Docker Compose: `docker compose logs postgres`).

  Не пускайте `pnpm db:check` срещу работна база: той проверява миграциите, като създава и трие временна база на същия сървър, и не казва нищо за бавни заявки или заключвания.

### Изследователят `/explore` (M05)

- **Няма какво да се пуска или настройва.** Подредбата на графа върви в браузъра на посетителя, в Web Worker с ELK, който се зарежда само на `/explore`; той няма нищо общо с фоновия `pnpm worker` (раздел 5). Страницата чете през същите процедури като браузъра (`lineage.start`, `lineage.ego`, `lineage.subtree`) и през същия кеш.
- **Какво виждат посетителите, когато базата не отговаря.** Провалено четене никога не се показва като празен запис: без избран човек вместо списъка с линиите пише **The lineages could not be loaded.** с **Retry**; ако не се зареди графът — **The lineage could not be loaded. Nothing was changed.** с **Retry**; в списъчния изглед (**List**) — **This profile could not be loaded** с **Retry**. „There is no public profile with this address in the record.“ означава само липсваща или скрита личност. **Retry** опитва същото четене отново.
- **Дневникът.** При такъв провал сървърът записва два реда, никога с адрес, име или заявката: на процедурата, например `rpc lineage.start failed: DrizzleQueryError (postgres 57014) request 01a1…`, и на страницата, само с кода: `[explore] the starting points could not be loaded: INTERNAL_SERVER_ERROR`, `[explore] the lineage could not be loaded: …` или `[explore] the person in focus could not be loaded: …`. Отделни редове при натоварване не са проблем; ако се появяват постоянно, проверете базата както за проверката на личността по-горе (`pg_isready`, `pg_stat_activity`, дневника на PostgreSQL).
- **Бюджетът.** `/explore` има собствен бюджет на JavaScript от 200 kB (раздел 9); `node scripts/check-bundle-budget.mjs` след `pnpm build` пада, ако страницата го надмине.
- **Мастилото и колоните (31.10.2026).** Няма нищо ново за пускане: подредбата слага всяка линия на изгледа в отделна колона, а платното рисува връзките в мастило от компактните карти нагоре (ADR 0005, точка 11, и ADR 0009, точка 11). Геометрията на мастилото идва с платното, не с първия JavaScript на страницата, затова бюджетът от 200 kB е същият. Базовите снимки на изследователя във визуалната регресия (раздел 9) са сменени с тези от CI.

### Превключвателят за грешки `WCR_TEST_FAULTS`

`WCR_TEST_FAULTS=lineage-once,person-once` е само за E2E тестовете на състоянията с грешка (Retry): Playwright го задава сам на сървъра, който пуска. Кодът му е **само в E2E сборката** (`pnpm build:e2e`, която `scripts/verify.sh` и CI правят); в обикновената `pnpm build` го няма. **Никога не го задавайте в `.env` на сървър, който ползват хора.** Ако е зададен, а `APP_URL` не е локален адрес (`localhost`, `127.0.0.1`, `[::1]`), сървърът отказва да тръгне със съобщение `WingChunRoots cannot start: WCR_TEST_FAULTS is a test switch and is refused unless APP_URL is a loopback host`. Махнете реда и пуснете отново. Дори зададен на локален адрес, той проваля само заявки, които носят специалната бисквитка на теста. `pnpm e2e` и `pnpm screenshots` искат E2E сборката: след обикновен `pnpm build` спират веднага, преди да пуснат сървъра, със съобщение `` … run `pnpm build:e2e` first … `` (`e2e/build-check.ts`). Обикновена сборка, пусната със `WCR_TEST_FAULTS`, отказва да тръгне: `WingChunRoots cannot start: WCR_TEST_FAULTS is set, but this build has no test switch …`.

### Измерване на заявките

`pnpm perf:queries` създава временна база на PostgreSQL сървъра от `TEST_DATABASE_URL` (от `.env` или от средата; локално това е базата от Docker Compose), зарежда измислен граф от около 100 000 връзки, мери всяка процедура и записва [`docs/perf/api.md`](../perf/api.md) с версията на PostgreSQL, времената и плановете. После трие временната база; другите бази не се пипат. Отнема около половин минута. Пуснете го отново след промяна на заявките, изгледите или индексите и включете новия `docs/perf/api.md` в commit-а.

### Проверки и визуална регресия

`scripts/verify.sh M04` проверява етапа: интеграционните тестове на услугата, E2E `@M04` (профил и списъчен изглед без JavaScript, еднаква страница за скрита и липсваща личност, поверителност, таван, двете грешки и Retry, основатели, телефон с текст 200 %, axe на телефон, при грешка и за влязъл участник), договора OpenAPI, че обикновената сборка няма превключвателя, отказа му при публичен `APP_URL` и документите. Пълният лог е в `.verify/M04.log`. От M04 визуалната регресия (§10) включва и `/people/demo-two-lineages` и `/people/demo-two-lineages/lineage`.

## 12. Тестови планове (`/admin/grants`, M08)

В пилота няма плащания. Вместо тях администраторът дава на акаунт по-висок план като **тестов план**. Матрицата на плановете, правилата и решенията по подразбиране са описани в [`docs/entitlements.md`](../entitlements.md).

### Достъп

**Administration** (`/admin`) → **Plan grants** (`/admin/grants`), или от таблото (**Me**): разделът **Staff work** казва колко заявки за пилотен достъп чакат отговор и води към тях („Answer them in Plan grants“). Страницата се отваря само за администратор, чиято сесия е минала втория фактор. Друг член на персонала или обикновен акаунт вижда „Not available“. Администратор, чиято сесия още не е въвела код, е пратен към **Security**, за да го въведе, и после се връща в **Plan grants**. Същото става, ако проверката изтече, докато формата е отворена: изпращането ви води към **Security**, без да даде или отнеме план. Същото важи и за API-то (`/api/v1/admin/grants…`): там отговорът е 403.

Докато сесията ви не е минала втория фактор, и таблото не показва данни на персонала: **Staff work** не казва колко заявки чакат, а предлага **Verify this session** (води към **Security** и после обратно в таблото). Известията за заявки тогава не казват кой е поискал и какъв план, а само „An account asked for pilot access. Confirm this session with your authenticator app to see who asked and for which plan.“ Паролата сама не стига до тези данни. **Review the request** в такова известие ви праща към **Security** и след кода отваря точно тази заявка, с попълнената форма.

Акаунт на персонала няма нужда от профил: без профил таблото показва само **Staff work** и ред, че профил трябва само ако и тренирате.

### Даване на план

1. Отворете **Give a test plan…** (разкриването е затворено, освен ако идвате от заявка или от току-що дадения план). Въведете **Account e-mail**, тоест адреса, с който акаунтът влиза.
2. Изберете **Plan** (нищо не е избрано предварително): **Premium Student** (само за Student акаунти) или **Professional Sifu** (само за Sifu акаунти). От M16 **Premium Student дава 10 снимки в галерията** (вместо 1 на Free Student), затова формата вече не казва, че планът не отключва нищо; другите му функции са планирани и акаунтът ги получава, когато дойдат.
3. Изберете **Kind**: **Test plan** или **Complimentary**.
4. Попълнете **Reason**. Причината е задължителна и остава в одитния журнал.
5. **Starts**: празно значи днес; планът важи от 00:00 UTC на този ден. **Ends** не е задължително: планът спира в 00:00 UTC на този ден, така че последният му цял ден е денят преди това (таблото на акаунта пише например „until 31 December 2026“). Без край планът няма край. И двете дати могат да са най-много две години напред, а началото — не преди днес; полетата за дата предлагат само тези дни.
6. Натиснете **Give the plan**.

Ако пропуснете нещо, сайтът изрежда наведнъж всичко, което липсва или е грешно (например „3 answers need a look“: адресът, планът и причината), а не по едно поле на опит.

Сайтът отказва:

- адрес, на който няма акаунт;
- план за другия вид акаунт;
- начало преди днес, начало или край повече от две години напред, край не след началото;
- същия план за дати, които се припокриват с вече дадения. Първо го отнемете или изберете дати след него. План, който започва в деня, в който предишният свършва, продължава го без празнина.

Акаунтът получава известие „Pilot plan added: …“ (ако планът започва по-късно — от кой ден). Даването се записва в одита като `grant.create`.

### Заявки „Request pilot access“

Когато Free Sifu стигне лимита си, подканата в таблото му предлага **Request pilot access**. Заявката не таксува нищо. Тя:

- праща на всеки администратор известие „Pilot access requested“ в таблото му (`/dashboard`);
- появява се най-горе в `/admin/grants`, под **Pilot access requests**.

Всяка заявка има два отговора и заявителят знае, че ще получи един от тях („An administrator either gives you the plan or closes the request, and you get a notification either way.“), затова отговаряйте на всяка:

- **Give Professional Sifu** (или **Review the request** в известието, което гласи например „Demo Asking Sifu asked for Professional Sifu.“) отваря формата, попълнена с адреса и плана, с фокус върху **Reason** (без JavaScript страницата се отваря направо на формата, без да мести фокуса). Остава да въведете причина и дати. Когато дадете плана, заявката се затваря. Ако смените имейла във формата, планът отива при другия акаунт, а заявката, от която сте тръгнали, остава отворена.
- **Close request…** под заявката → **Reason for closing** → **Close the request** затваря заявката без план. Причината е задължителна и остава само в одита (`pilot_access.close`). Акаунтът получава известие „Pilot access request closed“ без причината; планът му не се променя и може да поиска отново. На мястото на заявката остава ред, че е затворена; при следващото отваряне на страницата тя вече не е в списъка.

Всеки акаунт има най-много една отворена заявка и до 3 заявки за 30 дни; при лимита сайтът му казва от кой ден може да поиска отново. Ако акаунтът смени вида си (Student ↔ Sifu), отворената му заявка за план на стария вид се затваря сама. Когато няма отворени заявки, разделът пише „No pilot access request is waiting for an answer.“

Известието не пази името на заявителя. Таблото го взима от профила му при всяко отваряне, така че виждате текущото име. Ако акаунтът е изтрит, известието пише „A since deleted account …“ и няма връзка към заявка.

Известието следи и заявката. Когато на нея вече е отговорено (дали вие или друг администратор сте дали плана или сте я затворили), то гласи например „Demo Asking Sifu asked for Professional Sifu. The request has already been answered.“ и няма **Review the request**. Ако отворите стара връзка `/admin/grants?request=…` към такава заявка, формата не се отваря, а страницата казва „This pilot access request has already been answered. Nothing is waiting in it.“

### Таблицата и отнемането

**Grants** изрежда всички дадени планове, най-новите първи, по 20 на страница. Адресът на акаунта се вижда винаги целият: дълъг адрес се пренася на нов ред, най-често преди „@“. **Find by e-mail** търси по адрес (и в заявките). Заглавията на колоните **Account**, **Plan**, **Starts**, **Ends** и **State** сортират таблицата. Датите са кратки („19 Oct 2026“); пълната дата се вижда при посочване. Всичко работи и без JavaScript, а адресът на страницата пази търсенето и сортирането. На телефон (и на компютър при голям мащаб) всеки ред е карта, а сортирането е в лентата **Sort grants** над картите; всяка връзка в нея е достатъчно голяма за докосване (поне 44×44 px).

Състоянията са **Active**, **Starts later**, **Ended** и **Revoked**, всяко със знак и с текст. „Not in effect: other account type“ значи, че акаунтът е сменил вида си: планът важи отново, ако видът се върне.

Отнемане: **Revoke…** под реда → **Reason for revoking** → **Revoke Professional Sifu**. Само последният бутон е червен. Ако забравите причината, формата остава отворена с фокус върху нея; без JavaScript страницата се отваря направо на нея, в същия списък (търсене, сортиране, страница). Отнемането:

- се записва в одита като `grant.revoke`;
- праща на акаунта известие „Pilot plan ended: …“;
- **не пипа връзки:** потвърдените връзки остават потвърдени и публични. Отказват се само новите одобрения над безплатния лимит, а чакащите заявки остават чакащи. От M11 школите, които акаунтът е обявил, губят публичния си пин (и публичната си страница) веднага, без да бъдат изтрити; ново право ги връща без нов преглед (раздел 17).

### Одитът

Одитните записи са в `audit_log`. Те пазят идентификатори, плана и датите, но не и имена:

- `grant.create` и `grant.revoke`, с причината и администратора;
- `account.type_change` — смяна Student ↔ Sifu, с плана преди и след нея. Акаунт може да смени вида си до 5 пъти за 24 часа (след това 429), за да не пълни одита, който не може да се чисти;
- `pilot_access.request` и `pilot_access.close` (затворена без план, с причината и администратора).

### Когато нещо се обърка

Ако базата данни не отговори навреме (например друга операция държи реда на акаунта), формата остава отворена с попълнените полета и казва „Something went wrong on our side; nothing was changed. Try again.“ Наистина нищо не е променено: всяко даване, отнемане, затваряне и смяна на вида е една транзакция, заедно с отговора. В лога на сървъра остава един ред, например `rpc grants.create failed: DrizzleQueryError (postgres 57014) request 01a1…`: процедурата, видът на грешката, кодът на PostgreSQL и идентификаторът на заявката, без адреси, имена и входни данни. По идентификатора намирате заявката в журнала, без да търсите лични данни.

Същото важи, когато не успее четенето на страница. **Plan grants** (и таблото, и **Account type and plan**) показва тогава заглавието си, „We couldn't load the plan grants. Nothing was changed.“, „This is usually brief: try again in a moment.“, бутон **Try again** и **Back to administration**. **Try again** отваря отново същия адрес, със същото търсене, и работи и без JavaScript. Навигацията остава. В лога има същия един ред (`rpc grants.list failed: …`) и ред на Next.js с „Internal server error“ и `digest`, но никога текста на грешката от базата, търсения адрес или идентификатора на акаунт.

Пример с `psql` срещу локалната база:

```sql
SELECT occurred_at, action, actor_role, subject_id, reason, after
  FROM audit_log
 WHERE action IN ('grant.create', 'grant.revoke', 'account.type_change', 'pilot_access.request', 'pilot_access.close')
 ORDER BY occurred_at DESC
 LIMIT 20;
```

## 13. Имена, търсене и заявки за изтриване (M07)

### Ключове за търсене

Търсенето (палитрата, `Ctrl+K`) намира хора по ключове в таблицата `person_name_key`: латиница без диакритика, кирилица и нейната транслитерация, сгънати китайски йероглифи, пинин и Jyutping без тонове и хонконгски изписвания. Подробностите, праговете и ограниченията са в `docs/search.md`.

- Ключовете на един човек се пишат наново при всеки онбординг и запис на профила, в същата транзакция.
- `pnpm db:seed` поставя в опашката задачата `search.keys.rebuild`, а worker-ът я изпълнява (`pnpm worker`). В лога на worker-а остава ред като `search.keys.rebuild: wrote 6335 key(s) for 600 person(s)`, само с броеве.
- **`pnpm search:rebuild`** поставя същата задача в опашката: пуснете го след промяна в правилата (`src/server/search/keys.ts`, `aliases.ts`) или ако търсенето не намира хора, които със сигурност са публични. Задачата е идемпотентна и пише по 200 души на транзакция.
- Ако търсенето не намира нищо след `pnpm db:seed`, проверете дали worker-ът работи и дали ключовете са записани: `SELECT count(*) FROM person_name_key;`.

Ново хонконгско изписване се добавя като ред в `ALIAS_ROWS` (`src/server/search/aliases.ts`) със своя източник, след това `pnpm search:rebuild`.

### Заявки за изтриване на акаунт

Член на пилота иска изтриване от `/account/privacy` с **Request account deletion**. Тогава:

1. Отваря се случай в `review_case` с вид `deletion_request` и статус `open` (по един отворен случай на акаунт; повторната заявка връща същия).
2. Всеки администратор получава известие **Account deletion requested** с връзка **See deletion requests**, която води към `/admin#deletion-requests`.
3. Одитът записва `account.deletion_request` с идентификатора на случая, без име и адрес.

На `/admin` (администратор с потвърден втори фактор) частта **Account deletion requests** изброява отворените заявки: името на профила (с връзка към него), имейлът на акаунта, датата, статусът и идентификаторът на случая.

**Изпълнение по време на пилота.** Заявките за изтриване не са в опашката за преглед на M10a (раздел 15): по подразбиране остават на `/admin` и се изпълняват или затварят с командата **`pnpm account:delete`** на компютъра, на който работи пилотът (въпрос 2 в `docs/plan/questions/M10a.md`). Тя следва правилото по подразбиране (`DEFAULT`, въпрос 1 в `docs/plan/questions/M07.md`, до правния преглед). Стъпките, по ред:

1. **Потвърдете заявката.** Пишете на имейла от списъка на `/admin` (страницата `/account/privacy` казва на човека, че ще получи такова писмо и може да се откаже в отговора си).
2. **Копирайте идентификатора на случая** от реда на заявката в **Account deletion requests** на `/admin` (след думата „case“).
3. **Ако човекът се е отказал**, затворете случая без изпълнение:

   ```bash
   pnpm account:delete --case <идентификатор> --cancel
   ```

   Случаят става `dismissed`, акаунтът и профилът остават непроменени, одитът записва `account.deletion_cancel`.
4. **Иначе изпълнете заявката:**

   ```bash
   pnpm account:delete --case <идентификатор>
   ```

   В една транзакция командата:
   - изтрива имената на профила в оригиналната писменост и всички останали имена освен името за показване на латиница (ключовете им за търсене се изтриват с тях), биографията, града и годината на започване;
   - прави профила непоет исторически запис (`stewardship = unclaimed`, без акаунт), за да не изчезнат връзките, които учителите и учениците са потвърдили. Профилът остава публичен само ако е бил публичен **и** има потвърдена връзка; профил, публичен само със съгласието на собственика си, става частен (`involved_only`);
   - маха снимката на профила (от M14): редът ѝ става `removed`, `person.photo_id` се изчиства, файловете се трият след транзакцията, а във всички редове на снимките на профила (и по-старите) хешът на качения оригинал (`original_sha256`) се изчиства;
   - изтрива записите за съгласията (`consent_record`) на акаунта, както и при непотвърден акаунт;
   - архивира школите, които акаунтът е обявил (от M11, и черновите): статус `archived`, изтрити и извън картата, без контакти, уебсайт, описание, частна точка и инструктори (публичната точка се връща в центъра на града); отворените им случаи **School listing** се затварят (`dismissed`), а връзката към акаунта се маха;
   - пуска задачата `lineage.recompute` за линиите на профила, ако той става частен (филтърът по линия на `/schools` го изважда, щом worker-ът изпълни задачата);
   - затваря случая: статус `resolved`, решение `approved`, дата на решението; случаите на акаунта вече не сочат към него;
   - изтрива акаунта за вход заедно със сесиите, паролата, двуфакторното удостоверяване, известията и заявките му;
   - записва `account.delete` в одита (идентификатори и броеве, без имена и адреси). Одитът (`audit_log`) не се трие и не се променя.

   Командата работи само с база на същия компютър и отказва `NODE_ENV=production`, като `pnpm admin:create`. Ако друг запис още сочи към акаунта (например план, даден от този акаунт като администратор), командата спира с `CONFLICT` и **не изтрива нищо**. От M10a такъв запис са и качените доказателства, бележките по случаи за преглед и историята на връзките (`evidence_file`, `review_note`, `relationship_event`): акаунт, който е качил доказателство, засега не може да се изтрие с командата. Такава заявка остава отворена до решението за срока на съхранение на доказателствата (въпрос 1 в `docs/plan/questions/M10a.md`).
5. **Рестартирайте уеб сървъра** (спрете `pnpm start` или `pnpm dev` и го пуснете отново). Командата работи в отделен процес и не може да изчисти публичния кеш на сървъра (раздел 11), затова без рестарт изтритите имена и биографията може да се виждат на `/people/<адрес>` още няколко часа.

Ако собственикът избере друго правило (въпросът в `docs/plan/questions/M07.md`), стъпките се сменят с него. Докато заявката чака, акаунтът работи както досега.

Преглед на отворените заявки с `psql`:

```sql
SELECT rc.id, rc.status, rc.created_at, u.email
  FROM review_case rc LEFT JOIN auth_user u ON u.id = rc.opened_by_user_id
 WHERE rc.kind = 'deletion_request' AND rc.status IN ('open', 'in_review', 'needs_info')
 ORDER BY rc.created_at;
```

### Съгласия и одит на профила

- Оттеглено съгласие е нов ред в `consent_record` с `action = 'withdrawn'` и версията на документа; старите редове не се променят. Одитът записва `consent.withdraw`.
- Оттеглянето на `publication` (или махнатата отметка **Show my profile publicly**) прави профила частен (`person.visibility = 'involved_only'`) и изчиства публичния кеш на човека и на съседите му (DEFAULT D03, въпрос 2 в `docs/plan/questions/M07.md`).
- Всеки запис на профила е одитиран като `person.update`: видовете, писмеността и езика на имената, броя ключове за търсене, държавата, града, годината и видимостта преди и след промяната, но никога самите имена или биографията.

```sql
SELECT occurred_at, action, subject_id, before, after
  FROM audit_log
 WHERE action IN ('person.update', 'consent.withdraw', 'account.deletion_request')
 ORDER BY occurred_at DESC
 LIMIT 20;
```

## 14. Заявки към учител и одобрения (M09)

Как работят за членовете, е описано в ръководството за потребителя („Учители и ученици: заявки и одобрения“); решенията — в [ADR 0011](../adr/0011-teacher-requests.md). Тук е само това, което администраторът прави или проверява.

### Няма какво да се пуска

- Заявката, одобрението, отказът, повторното изпращане, оттеглянето и краят на обучението вървят в уеб процеса, през процедурите `relationships.*` (`/api/rpc` и `/api/v1`). Писмата и преизчисляването на линиите вървят през worker-а (раздел 5).
- **Без работещ worker** одобрението пак е записано, публично и видимо веднага: самата процедура изчиства кеша на двамата и на учителите над тях. Чакат само писмата и `lineage_membership`; те се изпълняват, щом worker-ът тръгне.
- **Персоналът не отговаря на заявки.** Рецензентите (модератор, архивист, администратор с потвърден втори фактор в сесията) виждат чакащите заявки в профила и в списъчния изглед на ученика и на учителя и през API-то, но не могат да ги одобрят, откажат или оттеглят (403). Без втория фактор в сесията виждат само публичния запис, като всеки посетител (DEFAULT D03).
- **Лимитът на Free Sifu** (5 одобрени ученици, DEFAULT D06) се налага при одобрението. Учител на лимита вижда подканата за по-висок план над чакащите заявки; заявките остават чакащи. Тестов план от `/admin/grants` (раздел 12) вдига лимита веднага.

### Вътрешното обновяване на кеша

Публичният кеш (`'use cache'`, раздел 11) живее в паметта на уеб процеса. Worker-ът е друг процес, затова след всяко преизчисляване на линиите праща таговете на уеб процеса: `POST /api/internal/revalidate` с `Authorization: Bearer <тайна>`.

- **Тайната.** `INTERNAL_REVALIDATE_SECRET` в `.env`, поне 32 знака. Празна (или по-къса): производна от `MAIL_SEAL_KEY`, който уеб процесът и worker-ът вече споделят, затова локално, в облачната сесия и в CI няма нищо за добавяне. Уеб процесът и worker-ът трябва да четат един и същ `.env`; иначе маршрутът отказва с 401.
- **Адресът.** `INTERNAL_APP_URL` (уеб процесът в мрежата на Docker Compose, когато приложението тръгне там, M12) или, празен, `APP_URL`. Маршрутът не трябва да е достъпен отвън; във Фаза 1 всичко е на един компютър.
- **Какво приема.** Само тагове на кеша (`person:<id>`, `lineage:<id>`, `lineage-membership:<id>`, `explore-start`), до 2000 наведнъж. Worker-ът праща само `lineage-membership:<id>`, по един на линия. Без тайната или с грешна тайна: 401, без да чете тялото; нещо друго вместо тагове: 400. Нищо друго не може да бъде изчистено през него.
- **Дневникът на worker-а.** Успех: `lineage.recompute: job <id>: 2 lineage(s), 41 member(s), 2 tag(s) revalidated`, само с броеве. Провал: `lineage.recompute: job <id>: attempt 1 of 6 failed (<код>); will retry`. pg-boss опитва отново до 5 пъти (след 10 s, после все по-дълго, до 5 min). Кодът казва какво да проверите:
  - `revalidate answered 401` — уеб процесът и worker-ът имат различни тайни: проверете `INTERNAL_REVALIDATE_SECRET` и `MAIL_SEAL_KEY` в средата на двата процеса и ги рестартирайте;
  - `revalidate unreachable (ECONNREFUSED)` — уеб процесът не работи или не е на този адрес: проверете `INTERNAL_APP_URL` и `APP_URL`;
  - `database error <SQLSTATE>` — базата (както в раздел 11, „Дневникът“);
  - `RevalidateSecretError` — няма нито `INTERNAL_REVALIDATE_SECRET`, нито `MAIL_SEAL_KEY` (`scripts/init-env.sh` ги създава).

  След `no attempts left` броячите на линиите остават стари, докато следващо одобрение в същата линия не пусне задачата отново; рестартът на уеб сървъра изчиства кеша (раздел 11).

### Одитът и историята

Всеки преход е ред в `relationship_event` (стар и нов статус, актьор и ролята му, ключ за идемпотентност) и запис в одита: `relationship.request`, `relationship.resubmit`, `relationship.approve`, `relationship.reject`, `relationship.withdraw`, `relationship.end` — с идентификатори, без имена и адреси. Нищо не се трие: оттеглена и отказана заявка остават като история, видими само за двамата.

```sql
SELECT occurred_at, action, subject_id, before, after
  FROM audit_log
 WHERE action LIKE 'relationship.%'
 ORDER BY occurred_at DESC
 LIMIT 20;
```

### Тестовете

E2E тестовете на M09 (`e2e/m09-requests.spec.ts`) създават свои акаунти (`demo-e2e-…@example.test`, с измислени имена `Demo …`) и ги свързват публично в демо линиите, а други тестове и визуалната регресия броят публичните хора. Затова вървят в проекта `exclusive`, в отделно пускане след останалите: `scripts/verify.sh` пуска `PW_EXCLUSIVE=1 pnpm e2e` след обикновеното `pnpm e2e`. На ръка: `pnpm build:e2e`, после `PW_EXCLUSIVE=1 pnpm e2e --grep @M09`. Създадените връзки остават в базата; демо данните както преди дава `pnpm db:reset && pnpm db:migrate && pnpm db:seed` (само локалната база или `TEST_DATABASE_URL`), както прави `scripts/verify.sh`.

## 15. Доказателства, опашка за преглед и архивна редакция (M10a)

Как изглежда искът за исторически учител за члена, е описано в ръководството за потребителя („Исторически учител и доказателства“); как работят хранилището, качването и достъпът — в `docs/evidence-and-review.md`; решенията — в [ADR 0012](../adr/0012-evidence-and-review.md). Тук е това, което администраторът настройва, решава и проверява.

### Хранилището на доказателствата

Доказателствата са файлове извън базата; в базата (`evidence_file`) са само идентификаторът, видът, размерът, хешовете и случайният ключ. Ключът не се показва никъде: нито на страниците, нито в API-то, нито в дневниците.

- **Локално с Docker Compose** доказателствата са в SeaweedFS (S3), в частния бъкет `wcr-evidence`. `scripts/init-env.sh` добавя в `.env` `S3_ENDPOINT=http://127.0.0.1:8333`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` и `S3_BUCKET_EVIDENCE`; ако `.env` е от по-стар етап, пуснете скрипта отново (той само добавя липсващите имена) и рестартирайте `docker compose up -d --wait`, за да създаде контейнерът бъкета със същите ключове.
- **Без `S3_ENDPOINT`** (облачна сесия, тестове) файловете са в `.storage/evidence` в хранилището (извън git), достъпни само за потребителя на сървъра. `EVIDENCE_STORAGE_DIR` сменя папката; папка в `public/` се отказва. `EVIDENCE_STORAGE=filesystem` или `s3` избира драйвера изрично.
- Във Фаза 1 `S3_ENDPOINT` може да сочи само към този компютър (`127.0.0.1`, `localhost`, `::1`) или към контейнера `seaweedfs`. Облачно хранилище идва с хостинга (план §3.3).
- **Няма presigned адреси.** Всяко изтегляне минава през `GET /api/evidence/<id>` с проверка на правата и запис `evidence.view` в одита. Не давайте на никого адреса на бъкета или ключовете от `.env`.
- **Резервно копие.** Базата и файловете се пазят заедно: копие само на базата пази записите без файловете. В Docker Compose файловете са в тома на SeaweedFS; без S3 — в `.storage/evidence`.
- `pnpm db:reset` изчиства само базата. В тестовата среда останалите файлове в `.storage/evidence` нямат запис и могат да се изтрият на ръка.
- **Срок на съхранение.** `retention_until` остава празно и нищо не се трие автоматично, докато собственикът не реши (въпрос 1 в `docs/plan/questions/M10a.md`).

Когато качване не минава, отговорът казва защо (`docs/evidence-and-review.md`, „Качване“): 411 без `Content-Length`, 413 над 20 MB, 415 за друг вид файл или изображение над 50 мегапиксела, 409 при 20 файла в случая (в спора: при 20 собствени файла на страната — всяка страна има свои 20, а отказът говори само за нейните; модераторът може да види до 40), 429 при над 20 файла без иск за 24 часа. Не вдигайте `experimental.proxyClientMaxBodySize` и не добавяйте `api` към matcher-а на `src/proxy.ts`: тогава тялото ще се буферира в паметта, преди сървърът да провери размера.

### Опашката `/admin/review`

Отваря се от **Review queue** на `/admin` и в **Staff work** на таблото. Само за модератори, архивисти и администратори, със сесия с потвърден втори фактор (иначе сайтът води към **Security** за кода). Друг влязъл потребител вижда изричното „You don't have access to the review queue…“. Уводът над таблицата казва кой решава всеки вид: архивист или администратор — историческите искове, исковете за профил и проверките на инструктор; модератор или администратор — сигналите и споровете.

Таблицата показва вида, хората, статуса, на кого е възложен случаят и датата, първо най-старите (връзката над таблицата обръща реда). **Filter the queue** филтрира по вид, статус и възлагане. Филтрите, редът и страницата са в адреса, затова връзката към филтрирана опашка може да се прати. Заявките за изтриване на акаунт не са тук (раздел 13).

| Действие | Кой |
|---|---|
| Отваря случая и чете бележките | модератор, архивист, администратор |
| **Assign to me** | всеки от персонала |
| **Assign** (дава случая на друг) | администратор: първо избира проверяващ в **Give the case to**. **Assign** без избран проверяващ се отказва със „Choose a reviewer from the list.“ и не променя възлагането |
| **Unassign** | проверяващият на случая или администратор; само този бутон маха възлагането |
| Отваря файловете и вижда имената им | проверяващият на случая (докато случаят е негов) и администраторите; за файл на архивен запис — качилият го архивист и администраторите. Другите (членът на персонала, на когото случаят не е възложен, и архивистът, който не е качил файла) виждат вместо името вида на файла (например „PDF file“) и размера, без връзка |
| **Verify the claim** | архивист на възложен му случай или администратор |
| **Refuse the claim** (с причина) | архивист на възложен му случай или администратор |
| **Ask for more information** (с въпрос) | проверяващият на случая или администратор |
| **Internal note** | всеки от персонала; ученикът не я вижда |

Резултатът на всяко действие (възлагане, решение, бележка, запис на архивна редакция) е съобщение, което взема фокуса, така че екранният четец го прочита веднага, и го взема отново при следващо действие. Потвърждението за добавена бележка е под бележките, където сте писали. Отказаното **Assign** без проверяващ показва причината под **Give the case to** и води фокуса там.

Никой не решава собствен иск (403): член на персонала, който е ученикът или учителят в иска, не може да го поеме, да реши, да поиска информация или да пише бележки; администраторът не може да му го възложи (той не е в списъка **Give the case to**), а когато отвори случая, вижда само това, което виждат страните — без вътрешните бележки. Модераторът може да вземе случай и да поиска информация, но не потвърждава и не отказва исторически искове: те са работа на архивистите. При нов иск всеки архивист и администратор получава известие **New historical teacher claim**; възложеният проверяващ получава известие, когато ученикът добави файлове или оттегли иска.

**Как се решава.** Прочетете бележката на ученика, отворете файловете (изтеглят се, не се отварят в страницата) и сравнете ги с името, линията и годините. Потвърждението прави връзката и двата профила публични веднага и пуска преизчисляването на линията в worker-а (раздел 14). Причината за отказ ученикът чете дословно: пишете неутрално и конкретно какво доказателствата не показват. „Нужна е информация“ връща иска на ученика; когато той добави файл, случаят се връща при вас (**In review**).

Всички действия са и процедури на API-то (`review.list`, `review.get`, `review.assign`, `review.decide`, `review.note`) и са идемпотентни: двоен клик записва едно решение.

### Архивната редакция

От `/admin/review` → **Archival records** → въведете адреса на записа (частта след `/people/`). Само архивист редактира записи, които платформата пази или които никой не е поел (`stewardship` `platform` или `unclaimed`): **Name in Latin letters**, **Name in its own script**, **Life status** и **Biography (English)**. Причината е задължителна, а **Link evidence** по желание качва нови файлове (същото поле като при иска), които се свързват със записа при запис. Свързват се само файлове, които архивистът е качил сам за редакцията: файл от иск на ученик не може да се свърже със запис, дори когато сте проверяващ на случая (и през API-то), защото така би станал четим за повече хора. Ако документ от иск трябва да остане и към записа, качете копие. Файл на архивен запис отварят качилият го архивист и администраторите; другите архивисти виждат вместо името вида му (например „PDF file“) и размера. Запис, който собственикът му поддържа сам, не се редактира оттук. Модераторът и администраторът без ролята на архивист могат само да отворят записа (403 при запис). Запис без промяна не пише нищо.

### Одитът

Всяко действие е ред в одита с идентификатори, видове и размери, без имена, имена на файлове и ключове:

- `evidence.upload`, `evidence.view` (всяко изтегляне, с вида на достъпа), `evidence.discard`;
- `person.create` и `relationship.request` при иск, `review.assign`, `review.note`, `review.needs_info`;
- `relationship.verify` или `relationship.reject` и `review.resolve` при решение;
- `person.update` при архивна редакция: актьорът, ролята му, причината и кои полета са променени.

Причината е в колоната `reason`, а файловете, на които се основава промяната, в колоната `evidence_ids` (`person.update`, а също `relationship.request` на иска и `relationship.verify` или `relationship.reject` на решението). Така се намират например всички промени, основани на даден файл:

```sql
SELECT occurred_at, actor_user_id, actor_role, action, subject_id, reason
  FROM audit_log
 WHERE evidence_ids @> ARRAY['<идентификатор на файла>']::uuid[]
 ORDER BY occurred_at;
```

Решенията и възлаганията са и редове в `relationship_event` (раздел 14).

```sql
SELECT occurred_at, actor_user_id, action, subject_id, after
  FROM audit_log
 WHERE action LIKE 'evidence.%' OR action LIKE 'review.%' OR action = 'person.update'
 ORDER BY occurred_at DESC
 LIMIT 20;
```

### Тестовете

- Интеграционните тестове (`pnpm test:int`) проверяват махането на EXIF и GPS, хешовете, лимитите (включително 413, преди тялото да се чете), заглавките при изтегляне, правата и решенията. Тестът на договора на хранилището (`src/server/storage/object-store.test.ts`, част от `pnpm test`) върви с файловата система навсякъде, а със SeaweedFS — където има `S3_ENDPOINT`: в средата (CI) или, ако средата го няма, в `.env` (както го четат `next start` и E2E тестовете). Затова локално с `.env` от `scripts/init-env.sh` той проверява и S3 драйвера, който приложението ползва; SeaweedFS трябва да работи (`docker compose up -d --wait`), иначе тестът пада с „The S3 store did not answer…“. Където `S3_ENDPOINT` няма нито в средата, нито в `.env` (облачна сесия), или където `EVIDENCE_STORAGE=filesystem`, S3 частта се отчита като пропусната („skipped“, с причината в името на теста), никога като минала. Непълни настройки (например `S3_ENDPOINT` без ключовете) карат теста да падне.
- E2E тестовете на M10a (`e2e/m10a-evidence.spec.ts`) правят връзки и хора публични, затова вървят в проекта `exclusive`, като тези на M09 (раздел 14). На ръка: `pnpm build:e2e`, после `PW_EXCLUSIVE=1 pnpm e2e --grep @M10a`.
- CI пуска SeaweedFS със същия образ и команда като `docker-compose.yml` (стъпката „Start SeaweedFS“), затова там доказателствата минават през S3.
- Новите ключови страници (`/dashboard/teachers/historical`, `/admin/review`, `/admin/review/records/demo-root-c`) и промененият `/dashboard/teachers` нямат базови снимки, докато не бъдат приети: първото изпълнение на CI пада на визуалната регресия, а снимките се приемат по раздел 10.

## 16. Покани, поемане на профил, проверка на инструктор, сигнали и арбитраж (M10b)

Как изглеждат поканата, поемането, проверката на инструктор, сигналът и арбитражът за члена, е описано в ръководството за потребителя („Покана към учител, поемане на профил, проверка на инструктор и сигнали“); правилата и решенията по подразбиране — в `docs/evidence-and-review.md` и [ADR 0013](../adr/0013-claims-reports-arbitration.md). Всичко минава през опашката `/admin/review` от раздел 15, с нови видове случаи.

### Кой какво решава

| Вид случай (**Kind**) | Отваря се, когато | Решава | Решенията |
|---|---|---|---|
| **Profile claim** | поканен учител приеме поканата (**Claim this profile**) | архивист на възложен му случай или администратор | **Approve the claim**, **Refuse the claim** (с причина), **Ask for more information** |
| **Instructor verification** | Сифу изпрати доказателства (**Send for verification**) | архивист на възложен му случай или администратор | **Verify the instructor**, **Refuse the verification** (с причина), **Ask for more information** |
| **Profile report** | член подаде **Report profile** | модератор на възложен му случай или администратор | **Uphold the report**, **Dismiss the report** |
| **Relationship dispute** | модератор или администратор постави връзка в арбитраж | модераторът, на когото е възложен (този, който го е отворил), или администратор | **Keep the link**, **Revoke the link**, **Ask for more information** — винаги с причина, която двете страни получават |

Всеки от персонала може да вземе случай за поемане на профил или за инструктор (**Assign to me**); спор и сигнал вземат само тези, които ги решават (модератор или администратор), защото проверяващият на спора отваря файловете и на двете страни. При нов случай известие получават онези, които решават този вид. Никой не решава случай, в който е страна (ученикът, учителят, поканеният, Сифу или човекът, за когото е сигналът). Всички действия изискват сесия с потвърден втори фактор.

В опашката случаите без връзка назовават профила си в колоната с хората: **Instructor** и името при проверка на инструктор, **Reported** и името при сигнал, така че два такива случая се различават (и в името на връзката за екранния четец).

Член на персонала, който е страна по случай от който и да е вид от M10b, го чете като страните: само своите файлове и отговори и публичните бележки на проверяващите, никога файловете и отговорите на друга страна; в опашката редът брои само неговите файлове. Страна, която не е отворила случая (човекът, за когото е сигналът, ученикът на поета връзка), не вижда фактите по случая (причината и подробностите на сигнала) и причината на решението. Историческият иск запазва правилото на раздел 15.

### Поемането на профил

Картата показва записа, който ученикът е създал (с надписа **Unclaimed record**), заявката, на която отговаря поемането (**The request it answers**), и бележката на поканения. Проверете дали поканеният е човекът от записа: името на акаунта му, бележката, при нужда **Ask for more information**. Доказателствата на ученика към заявката отварят само администраторите; поканеният ще ги види едва след одобрението.

- **Approve the claim** прави записа профил на поканения (още не е публичен) и премества заявката от **Waiting for the teacher to join** в **Waiting for the teacher**: учителят после я одобрява или отказва сам. Записва `relationship_event` (`awaiting_claim → pending_teacher`, причина `person_claim_approved`) и одит `person.claim` и `relationship.claimed`.
- **Refuse the claim** оставя заявката да чака учителя; ученикът може да прати нова покана, а поканеният чете причината на страницата на иска.
- Ако междувременно поканеният е създал собствен профил или ученикът е оттеглил заявката, одобрението се отказва с причината; откажете иска.

Поканата: 32 случайни байта, в базата само SHA-256 (`invitation.token_hash`), важи 14 дни и веднъж. Адресът на поканения не се вижда никъде в администрацията и се изтрива 30 дни след края на поканата (`retention.purge`, раздел 7), включително копието в записа за изпратеното писмо. Ученик може да прати до 3 покани за една заявка и до 10 общо за 24 часа; таванът важи и при едновременни изпращания. Отменена покана и покана, използвана от друг акаунт, отговарят като непозната връзка (404). Ученикът, създал записа, го вижда целия само докато никой не го е поел; след одобрения иск вижда само имената, докато учителят не отговори.

### Проверката на инструктор

Картата показва профила, файловете (отваряте ги, когато случаят е ваш) и бележката на Сифу. **Verify the instructor** записва одит `instructor.verify` с файловете, на които се основава решението; от този момент профилът казва **Instructor**, а надписът **Approved by an unverified instructor** изчезва от връзките, които Сифу вече е одобрил. Опорните Сифу в тестовите данни (`demo-free-sifu-5`, `demo-pro-sifu-8`) са потвърдени. Отворен може да е само един случай на човек.

### Сигналите

Картата показва причината (**Reason**), подробностите и профила. Сигналът **не скрива нищо сам**. Ако профилът наистина е подвеждащ или нарушава права, поправете го с архивна редакция (архивист, раздел 15) или като администратор и тогава **Uphold the report**; иначе **Dismiss the report**. Подалият сигнала не получава известие за решението (въпрос 3 в `docs/plan/questions/M10b.md`). Един акаунт може да подаде един сигнал за даден профил (уникален индекс `content_report_one_per_reporter_key`) и до 10 сигнала за 24 часа.

### Арбитражът (D19)

Постави се от **Archival records** → записа → **Set in arbitration** до потвърдена връзка, или направо на `/admin/review/arbitrate/<идентификатор на връзката>`. Само модератор или администратор, който не е страна. **Reason** е задължителна: двете страни я четат в известието, в имейла и на страницата на случая, затова пишете какво е оспорено и какви доказателства биха го решили.

След **Set in arbitration**:

- връзката е `in_arbitration`; публичните страници я показват като **Disputed** (с думи и с печата), а линията и профилите остават публични;
- отваря се случай **Relationship dispute**, възложен на вас, в състояние **Needs information**; двете страни получават известие **Relationship in arbitration** и имейл с причината и връзка към `/dashboard/cases/<id>`, където пращат файлове и отговор;
- одитът `relationship.arbitration` пази причината; `relationship_event` пази прехода `verified → in_arbitration`.

Когато страна отговори, случаят се връща при вас (**In review**). Всяка страна вижда само вашите бележки и своите отговори и файлове. Всяка страна може да прати до 20 файла, броени поотделно, така че една страна не запълва случая за другата; вие виждате до 40. **Keep the link** връща връзката във **Verified**; **Revoke the link** я отменя (`revoked`): тя излиза от публичната линия и линията се преизчислява. И двете искат причина, която двете страни получават с известие и имейл (одит `relationship.arbitration` или `relationship.revoke`).

### Одитът и историята

Нови действия в одита: `invitation.create`, `person.claim`, `relationship.claimed`, `instructor.request`, `instructor.verify`, `report.create`, `review.reply`, `relationship.arbitration`, `relationship.revoke`; както досега `review.assign`, `review.needs_info`, `review.resolve`. В одита няма имейл, токен или име. Историята на случаите от тези видове е в `review_event`:

Извършителят на ред в `review_event` е `ON DELETE SET NULL`: историята на случая остава и не спира `pnpm account:delete`. Акаунт, който е автор на бележка по случай, е качил доказателство, е свързал файл, е извършител в `relationship_event` или е изпратил покана, все още получава CONFLICT от `pnpm account:delete` (ограничение от M09/M10a).

```sql
SELECT e.created_at, c.kind, e.action, e.from_status, e.to_status, e.actor_role
  FROM review_event e JOIN review_case c ON c.id = e.review_case_id
 ORDER BY e.created_at DESC
 LIMIT 20;
```

## 17. Школи, карта и прегледът на обявите (M11)

Подробно описание: [`docs/schools-and-map.md`](../schools-and-map.md); решенията — [ADR 0014](../adr/0014-schools-map.md).

### След обновяване до M11

`pnpm db:migrate` прилага миграцията на M11 (нови колони на `place` и `school`, статусът `published` става `active`, нов `v_public_school`). После заредете градовете от GeoNames:

```bash
pnpm geo:load       # около 5200 града; db:seed (и db:reset) го правят сами
```

Командата е безопасна за повторение: записва само променените градове и пази идентификаторите им.

### Картата и стиловете

Картата на `/schools` взема стиловете и плочките си от OpenFreeMap (`tiles.openfreemap.org`): светъл стил Positron и тъмен Dark (`src/server/geo/map-styles.ts`). Нужни са интернет и достъп до този адрес; ключ не трябва. В облачната сесия адресът е блокиран, затова стиловете не са проверени там (въпрос 4 в `docs/plan/questions/M11.md`): отворете `/schools` веднъж в `pnpm dev` и проверете двете теми.

- `MAP_STYLES=local` в `.env` (празно по подразбиране) ползва локалните тестови стилове от `public/map-styles/` — само фон и мрежа, без външни заявки. E2E билдът (`pnpm build:e2e`) ги ползва винаги.
- Атрибуцията на OpenStreetMap и OpenFreeMap е в ъгъла на картата и в `/legal/licenses`; черновата на политиката за поверителност посочва OpenFreeMap като получател.

### Градовете (GeoNames)

Градовете са в `src/server/geo/data/geonames-places.tsv` (CC BY 4.0): България, Гърция, Германия, Обединеното кралство, САЩ и Хонконг. Записаното извлечение е от копие на дъмпа на GeoNames от 2020 г. (npm пакета `cities-with-1000` 1.0.4), защото официалният сървър не се отваря от облачната сесия. За да го обновите от официалния дъмп (предложението по подразбиране, въпрос 1):

1. Изтеглете `cities1000.zip` и `alternateNamesV2.zip` от <https://download.geonames.org/export/dump/> и ги разархивирайте извън хранилището, например в `~/Downloads/geonames/`.
2. ```bash
   pnpm geo:extract --cities ~/Downloads/geonames/cities1000.txt \
     --alternate-names ~/Downloads/geonames/alternateNamesV2.txt \
     --source "GeoNames cities1000.txt and alternateNamesV2.txt of $(date +%Y-%m-%d)"
   git diff --stat src/server/geo/data/     # прегледайте промяната
   pnpm geo:load
   ```
3. Направете commit на файла в отделен PR. Друга държава се добавя само след решение на собственика (в `src/server/geo/geonames.ts`, `EXTRACT_COUNTRIES`).

### Прегледът на обявите в `/admin/review`

Когато Сифу с Professional Sifu изпрати школа за преглед, в опашката се появява случай от вид **School listing**, а модераторите и администраторите получават известие. Картата на случая (**The listing**) показва името, града, как е показано местоположението, точката (само при точно местоположение; при „само град“ — „The map shows it at the centre of …; its address stays private.“), контактите, формите, описанието, инструкторите и дали акаунтът има Professional Sifu сега (ако няма, обявата може да бъде одобрена, но пинът няма да се покаже).

| Действие | Кой |
|---|---|
| **Assign to me**, **Internal note** | всеки от персонала |
| **Approve the listing** | модератор или администратор (по подразбиране, въпрос 5 в `docs/plan/questions/M11.md`) |
| **Return it to draft** (с причина) | модератор или администратор |
| **Ask for more information** (с въпрос) | проверяващият на случая или администратор |

**Повторен преглед.** Обявена школа остава на картата, когато Сифу я редактира, но промяна на името, града, начина на показване на местоположението, точния пин, уебсайта или инструкторите отваря отново случай **School listing** (по подразбиране, въпросът „Edits of a listed school“ в `docs/plan/questions/M11.md`; втора редакция се присъединява към отворения случай). Картата на такъв случай казва „This school is listed. Its Sifu changed it after the approval, and the changes are public now. …“: **Approve the listing** оставя школата обявена с промяната, а **Return it to draft** (с причина) я сваля от картата. Контактите, описанието и формите не отварят преглед.

**Обявата се е сменила.** Решението носи версията на обявата, която картата на случая показва. Ако Сифу я е редактирал, след като сте отворили случая, решението се отказва с „The Sifu changed this listing after you opened it. Open the case again and review the new details before you decide.“: отворете случая наново и прегледайте новите данни.

Никой не решава собствена обява. Как се решава: проверете дали името и контактите са на истинска школа по Wing Chun, дали градът и пинът си отговарят (точното място трябва да е до 50 km от града) и дали описанието не съдържа лични данни на други хора. Причината за връщане Сифу чете дословно в таблото си: пишете неутрално какво да поправи. Одобрението прави школата обявена (`active`) веднага: пинът се показва, докато акаунтът има Professional Sifu.

### Пинът и Professional Sifu

- Пин има само школа, обявена от акаунт с Professional Sifu (тестов план в пилота, раздел 12). Школите на демо данните нямат обявил ги акаунт и се показват, докато са активни (въпрос 2).
- Отнемането или изтичането на плана скрива пина и публичната страница веднага (изтичането по дата — до няколко минути, колкото живее кешът); школата остава `active` за Сифу. Ново право връщат пина без нов преглед.
- Точният адрес на школа „само град“ не се вижда никъде публично, нито от персонала в опашката.
- Публичните инструктори на школа са главният инструктор и онези, чиято учебна връзка с него е потвърдена; връзка, отменена или оттеглена по-късно, сваля човека от страницата на школата и от филтъра по линия. Филтърът по линия следва и човек, който скрие или покаже отново профила си (задачата `lineage.recompute`).

### Одитът

`school.create`, `school.update`, `school.submit`, `school.confirm`, `school.publish`, `school.return`, а при решение и `review.assign`, `review.note`, `review.needs_info`, `review.resolve`. Записите казват кои полета са се променили, никога точка, адрес или контакт.

Историята на случай **School listing** е в `review_event`, както при другите видове (заявката в раздела за M10b): `open` при изпращане или при редакция, която отваря преглед, `assign`/`unassign`, `needs_info`, `evidence`, когато Сифу изпрати обявата отново, и `approve` или `reject`. Повторено решение със същия ключ не прави нищо ново; ключ, който вече сте ползвали за друго действие, се отказва с „This request key was already used for another change. Reload the page and try again.“.

```sql
SELECT occurred_at, actor_user_id, actor_role, action, subject_id, reason
  FROM audit_log
 WHERE action LIKE 'school.%'
 ORDER BY occurred_at DESC
 LIMIT 20;
```

### `/admin/system`

Страницата е за персонала (модератор, архивист, администратор) със сесия, минала втория фактор; от `/admin` води връзката „System status“. Без втория фактор тя праща към `/account/security`, а на обикновен акаунт казва „Not available“. Показва:

- **Waiting jobs** — задачите, които чакат в опашката, и колко от тях са готови да тръгнат сега; по опашки, с „Waiting long“, ако готова задача чака повече от 15 минути (worker-ът е спрял или не смогва);
- **Failed jobs** — задачите, паднали след последния си опит, с опашката, часа и броя опити (никога съдържанието им);
- **Failed e-mail deliveries** — писмата, които не са стигнали след всички опити, и колко чакат да се изпратят;
- **Last backup** — кога е направен последният локален архив на базата, името и размерът на файла и дали има `.sha256`.

Състоянието е с текст и знак („Needs attention“ или „OK“), не само с цвят. Същите данни дава `GET /api/v1/admin/system`. Бутонът „Refresh“ чете наново.

## 20. Снимки на профила (M14)

Всеки акаунт може да сложи една снимка на собствения си профил (ръководството на потребителя, „Снимка на профила“). Решенията и причините са в [ADR 0016](../adr/0016-profile-photos.md).

### Какво се пази и къде

- Качването е процедурата `photos.upload`: сайтът я вика през `/api/rpc`, а бъдещото мобилно приложение през `POST /api/v1/photos/upload` (multipart, поле `file`). Заявка без `Content-Length` се отказва с 411, а над 5 MB (с малко място за самата форма) — с 413, преди тялото да се прочете. Всяко друго тяло към API (JSON) има граница 1 MiB: с обявен по-голям `Content-Length` е 413 веднага, а без `Content-Length` (chunked) се брои, докато се чете, и щом мине границата, четенето спира с 413.
- Видът се познава по първите байтове (JPEG, PNG, WebP). Изображението се декодира с ограничението за пиксели на доказателствата, завърта се по EXIF, изрязва се квадрат от средата и се записва наново като WebP с размери 96 и 512 пиксела. Метаданни (EXIF, GPS, XMP, ICC) не се копират.
- Файловете са в **отделно хранилище за снимки**, никога в това на доказателствата:
  - `MEDIA_STORAGE` — `filesystem` или `s3`; по подразбиране следва `EVIDENCE_STORAGE` (в облачна сесия с `EVIDENCE_STORAGE=filesystem` снимките също са на диска);
  - `MEDIA_STORAGE_DIR` — папката на диска, по подразбиране `.storage/photos` (не е в git); не може да е в `public/`, нито в папката на доказателствата или около нея;
  - `S3_BUCKET_MEDIA` — кофата в SeaweedFS, по подразбиране `wcr-media`; ако съвпада с `S3_BUCKET_EVIDENCE`, приложението отказва да тръгне.
- Ключът на файла е случаен (`photos/<48 шестнадесетични знака>/96` и `/512`) и никога не излиза навън. Таблицата е `person_photo` (статус `active`, `replaced` или `removed`, кой и кога), а `person.photo_id` сочи текущата снимка. Ролята `app_public_ro` не чете таблицата; публичният изглед `v_public_person` дава само `photo_id` и хеша на текущата снимка на публичен човек.

### Адресите и кешът

- Снимката се отваря от `GET /api/photos/<id>/<първите 16 знака от SHA-256>/<96|512>.webp`. Адресът се сменя с всяка нова снимка, затова старият отговаря с 404 веднага след смяна или махане.
- Снимка на **публичен** човек: `Cache-Control: public, no-cache` и `ETag`: всеки кеш пита сървъра при всяко ползване и получава 304 при същия `If-None-Match`, затова махане, скриване на профила или изтриване на акаунта важат веднага, без чакане на кеш. Снимка на **скрит** човек: само за собственика и за персонала с минат втори фактор, с `Cache-Control: private, no-store`; за всички останали — 404, както и страницата му.
- Отговорът винаги има `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` и `Cross-Origin-Resource-Policy: same-origin`. Грешка при четене се записва в лога с един ред без адреса и без човека.
- Файлът се чете от хранилището цял, с общ срок от 5 s. Ако SeaweedFS (или папката) не го даде навреме или върне грешка, адресът отговаря веднага с **503** (`no-store`), а в лога остава ред `[photos] store unavailable: <име на грешката> request <id>`; страницата се зарежда без снимката (браузърът показва текста от `alt` или празно място със същия размер). Много такива редове значат, че хранилището за снимки е бавно или спряло: проверете `docker compose ps` и логовете на `seaweedfs`.

### План и квота (D07)

Текущата снимка се брои за **1** срещу `photos` на плана (DEFAULT D07); смяната не добавя нищо, защото единицата е човекът. Ограничението е 5 MB на файл. Броенето е в `src/server/entitlements/access.ts`. От M16 функцията е „now“ и се прилага за цялата галерия (раздел 22).

### Махане от модератор

1. Потребител подава **Report profile** и пише, че става дума за снимката (подсказката на полето **Details** го споменава).
2. На картата на случая в опашката (`/admin/review/<id>`) има раздел **Profile photo** със снимката и формата **Remove photo**, когато случаят е за човек със снимка, а вие сте модератор, архивист или администратор с минат втори фактор.
3. **Reason for removing the photo** е задължителна. **Remove photo** трие файловете, записва статус `removed` с вас и причината и пише `photo.remove` в одита с причината. Притежателят може после да качи друга снимка.

Същото през API: `POST /api/v1/photos/remove` с `{ "slug": "<адрес>", "reason": "<причина>" }`. Без `slug` (или със собствения адрес) процедурата маха собствената снимка на акаунта. Ако сте персонал с минат втори фактор и дадете причина, и собствената ви снимка се маха като от модератор: причината се пази и одитът казва `staff`; без причина (или от обикновен акаунт) това е махане от собственика и причина не се пази. Качването се записва в одита като `photo.upload` (без файла и без името).

### Демо данни

`pnpm db:seed` генерира абстрактни изображения (кръг с четка, щрихи и червен печат на хартия — никога лице или снимка) за шестима демо души: `demo-root-b`, `demo-hub-b`, `demo-two-lineages`, `demo-cjk-name`, `demo-converging` и `demo-pro-sifu-8`. Останалите показват монограма. Изображенията са детерминирани, затова хешът на демо данните не се мени между две зареждания. Ако хранилището за снимки не е достъпно при зареждането, seed-ът продължава без снимките и го казва в отчета си.

### Проверка

`scripts/verify.sh M14` пуска unit тестовете (обработката, хранилището, ограничението на тялото), интеграционните тестове (`src/server/services/photos.int.test.ts` и редовете за снимките в матрицата за оторизация), сборката с бюджетите на JavaScript и E2E `@M14` в изключителното пускане (`e2e/m14-photos.spec.ts`: собственикът качва снимка само с клавиатура, вижда я в профила, на картата в изследователя и в реда на списък; axe в двете теми; накрая я маха). ## 21. Организации (M15)

Федерации, асоциации и групи школи кандидатстват, рецензентите ги одобряват, а одобрената организация има публична страница и табло (ръководството на потребителя, „Организации“). Решенията и причините са в [ADR 0018](../adr/0018-organizations.md).

### Преглед на кандидатура

- Кандидатурата отваря случай **Organization application** в опашката (`/admin/review`); редът показва името и държавата на организацията. Получавате известие като за другите случаи.
- Картата на случая (`/admin/review/<id>`) има раздел **The organization**: вид, седалище, уебсайт, ръководител, приблизителен брой школи и одобрението. Подкрепящият документ (ако има) е в **Evidence** и се отваря само след като поемете случая (или като администратор).
- **Approve the organization** и **Decline the application** са за архивист или администратор (DEFAULT, като проверката на инструктор); всеки рецензент може да поеме случая, да попита кандидата и да пише бележки. Кандидатът и администраторите на организацията не я преглеждат.
- Одобрението се изпраща с версията на кандидатурата от картата: ако кандидатът я е променил, след като сте я отворили, решението се отказва — отворете случая отново.
- Одобрението пуска публичната страница и **не дава план**, не проверява членове и не пише учителски връзки (DEFAULT D04, D12). Отказът иска причина, която кандидатът чете; организацията остава частна.

### План Federation

- `/admin/organizations` (само администратор с минат втори фактор, връзка **Organizations** от `/admin`) показва всяка организация с **Approval** и **Plan** поотделно.
- На страницата на организация: **Give Federation** — вид (**Test plan** или **Complimentary**), задължителна причина, начало и край (празни: от днес, без край). Само за одобрена организация без действащ или насрочен план. Одит `grant.create`. Нищо не се плаща; цената на Federation остава „Proposed price (not final)“ (DEFAULT D09).
- **Revoke** с причина (одит `grant.revoke`) затваря само управлението на членове и школи. Членовете, приетите школи, публичната страница, администраторите на организацията и личните планове на хората остават (DEFAULT D08).
- Същото през API: `GET /api/v1/admin/organizations`, `GET /api/v1/admin/organizations/<id>`, `POST /api/v1/admin/organizations/grant`, `POST /api/v1/admin/organizations/revoke-grant`.

### Права и поверителност

- Администраторите на организация са **акаунти** (`organization_admin`, роли `owner` и `admin`), отделни от членството на хора. Акаунт вижда и променя само организациите, които управлява: за всяка друга отговорът е 404.
- Чакаща организация редактира само своята кандидатура (DEFAULT, ADR 0018); одобрената не сменя името, вида и държавата.
- Публичната страница чете само одобрените организации (`v_public_organization`), публичните членове (`v_public_person`, D03) и публичните школи с приета връзка, само с града. Ролята `app_public_ro` няма права върху таблиците на организациите, нито върху изгледа; страницата го чете през `app_rw` и показва само публичния DTO.
- Одит: `organization.apply`, `update`, `approve`, `reject`, `admin_add`, `admin_remove`, `member_add`, `member_end`, `school_request`, `school_answer`, `school_end`. Известия: `organization.reviewed`, `organization.admin_added`, `organization.school_requested`, `organization.school_answered` (без имейли).

## 22. Галерии на профила и на школата (M16)

Всеки акаунт има галерия на собствения си профил, а школата — лого и снимки на залите (ръководството на потребителя, „Галерия на профила (M16)“). Решенията и причините са в [ADR 0019](../adr/0019-galleries.md); отворените въпроси с решенията по подразбиране — в `docs/plan/questions/M16.md`.

### Данни и хранилище

- Снимките на галерията са в `person_photo` (ADR 0016): единствената `active` е снимката на профила (`person.photo_id`), другите показани са `gallery`; колоните `caption`, `position`, `full_width`, `full_height`. Снимките на школите са в `school_photo` (`kind` `logo` или `room`, статус `active`, `replaced` или `removed`, кой, кога и защо е махнал; едно активно лого на школа). Ролята `app_public_ro` не чете нито една от двете таблици.
- Файловете са в хранилището за снимки (`MEDIA_STORAGE`, раздел 20): `photos/<ключ>/96`, `/512` и `/full` (цялата снимка до 1280 px). Адресите: `GET /api/photos/<id>/<хеш>/<96|512|full>.webp` и `GET /api/school-photos/<id>/<хеш>/<96|512|full>.webp`, със същите правила за видимост и кеш като в раздел 20.
- Всяка версия се кодира наново без EXIF, GPS, XMP и IPTC: снимка от залата на школа „само град“ не издава точното място. В логовете и одита има само id, размери и хешове.

### Право по план (DEFAULT D07, D13)

- `photos` вече е „now“ и се прилага (матрица `2026-11-03.1`, `docs/entitlements.md`): Free Student 1, Premium Student 10, Free Sifu 2, Professional Sifu 100, Federation без граница. Всяка снимка на галерията се брои, и тази на профила. Над границата `gallery.add` отговаря с `ENTITLEMENT_REQUIRED`, а страницата `/dashboard/photos` показва предложението за по-висок план.
- По-висока граница се дава само с план в `/admin/grants` (раздел 12): например **Premium Student** на Student акаунт дава 10 снимки.
- **D13:** доказателствата (`evidence_file`) никога не се броят и никога не са в галерията.
- Школата: едно лого и до **12** снимки на залите (`SCHOOL_ROOM_PHOTOS_MAX`, DEFAULT D07 (M16)); над границата `CONFLICT`. Не се броят срещу `photos` на никого.

### Кой какво може

- Галерията променя само акаунтът, чийто е профилът; снимките на школа — само акаунтът, който я е обявил (`school.created_by_user_id`). Персоналът не качва и не подписва.
- **Модерация:** персонал с минат втори фактор маха чужда снимка само с причина. На картата на случая за човек (сигнал, поемане на профил) разделът **Other photos of the gallery** има **Remove photo** за всяка снимка на галерията; на картата на случая за обява на школа разделът **The school's logo and photos** има същото за логото и залите. Причината се пази в реда и в одита (`gallery.remove`, `school_photo.remove`, с `by: staff`). Същото през API: `POST /api/v1/gallery/remove` или `POST /api/v1/schools/photos/remove` с `{ "photoId": "<id>", "reason": "<причина>" }`.
- Одитът записва и `gallery.add`, `gallery.update` (само че подписът е сменен, не текста му), `gallery.reorder`, `gallery.profile`, `school_photo.upload`, `school_photo.update` и `school_photo.reorder`.
- Изтриването на акаунт (`pnpm account:delete`) маха всички снимки на галерията (редовете остават `removed`, файловете се трият, `original_sha256` се изчиства); архивирането на обявените школи маха и техните снимки.

### Картата в изследователя

Пълната карта е 264×64 (беше 200×64): отпред квадратната снимка или монограмът, висок колкото картата. На телефон (платно, по-тясно от 640 px) пълните карти се показват от мащаб около 0,58 вместо от 0,75, за да се събират две една до друга на 390 px както преди; текстът им на телефон е по-дребен (решение на собственика, въпрос 2 в `docs/plan/questions/M16.md`, ADR 0019 §9). На компютър и таблет нищо не се сменя. Визуалните еталони на изследователя, на профила и на школите със снимки се сменят и се приемат само от CI (раздел 10).

### Демо данни и проверка

`pnpm db:seed` дава (D20, генерирани изображения) още две снимки в галерията на `demo-pro-sifu-8` (Professional Sifu, до 100 снимки; `demo-two-lineages` е на Free Student и има само снимката на профила), лого и две зали на `demo-school-sofia` (`demo-school-city-only` е без снимки). `demo-school-sofia` е обявена от `demo-pro-sifu-8`: с този акаунт **Your schools** в таблото води към **Logo and photos** (`/dashboard/schools/<id>/photos`). Когато акаунт има повече снимки, отколкото планът му включва (след по-нисък план или изтекъл грант), нищо не се маха: редът казва „You have 3 photos; Free Student includes 1. Remove 3 to add another.“ `scripts/verify.sh M16` пуска unit тестовете (обработката без метаданни, логото, плановете), интеграционните тестове (`src/server/services/gallery.int.test.ts`, `src/server/services/school-photos.int.test.ts` и редовете в матрицата за оторизация), сборката с бюджетите и E2E `@M16` (`e2e/m16-gallery-viewer.spec.ts` на компютър и телефон; `e2e/m16-galleries.spec.ts` в изключителното пускане).

## 23. Календар на събитията (M17)

Семинари, лагери, изпитни сесии и други събития: всеки разглежда `/events`, Sifu публикува в рамките на плана си (ръководството на потребителя, „Календар на събитията (M17)“). Решенията и причините са в [ADR 0020](../adr/0020-events.md); отворените въпроси с решенията по подразбиране — в `docs/plan/questions/M17.md`.

### Данни

- Таблици `event` и `event_instructor` (`docs/data-model.md`); ролята `app_public_ro` чете само изгледа `v_public_event` (публикувани и отменени събития, организатор, инструктори и школа само докато са публични, от школата само името и градът).
- Плакатът е в хранилището за снимки (`MEDIA_STORAGE`, раздел 20), с адрес `GET /api/event-posters/<id>/<хеш>/<96|512|full>.webp`; кодиран наново без EXIF, GPS, XMP и IPTC. Не е в галериите и не се брои срещу `photos`.
- `GET /events/<slug>/calendar.ics` е файлът „Add to calendar“ (RFC 5545, времената в UTC).
- Всички времена се пазят като момент (`timestamptz`) и часовата зона на събитието; страниците ги показват в зоната на събитието, за всеки зрител.

### Право по план (DEFAULT M17, въпрос 1; DEFAULT D25)

- `events` е „now“ и се прилага (матрица `2026-11-05.1`, `docs/entitlements.md`). **Professional Sifu**: до 3 публикувани събития (решение на собственика от 05.11.2026; преди 2), които започват в един календарен месец в зоната на събитието; отменено или махнато не се брои; преместване в друг месец се проверява наново. Броенето е под заключването на квотата, затова две едновременни публикации не минават границата заедно.
- **Free Sifu**, Student акаунти и организация без Federation: `ENTITLEMENT_REQUIRED` (`details.entitlement` казва защо). Professional Sifu се дава в `/admin/grants` (раздел 12); **Federation** на организация — в `/admin/organizations` (раздел 21), и тогава организацията публикува без граница.

### Модерация (DEFAULT M17, въпрос 2)

Събитията се публикуват **без преглед**. Персонал (модератор, архивист или администратор) с минат втори фактор вижда на страницата на всяко събитие раздела **Moderation** с **Reason** и **Remove the event**. Причината е задължителна и се пази само в реда (`removal_reason`) и в одита (`event.remove`); организаторът и публиката не я виждат. След махане: събитието изчезва от `/events`, от профилите и от школите; страницата му казва **This event is not listed** (статус 200 и `noindex`, както при школа, която не е обявена); `events.get`, `.ics` и плакатът отговарят 404; в таблото на организатора то е със статус **Removed**. Махането не се връща от интерфейса. Същото през API: `POST /api/v1/events/remove` с `{ "id": "<id>", "reason": "<причина>" }`.

Одитът записва още `event.create`, `event.update`, `event.cancel`, `event.poster_upload` и `event.poster_remove` (само идентификатори и полета, които са се сменили; никога текст или ключ на файл в лога). Изтриването на акаунт (`pnpm account:delete`) маха собствените събития на Sifu и трие плакатите им.

### Известия (DEFAULT M17, въпрос 3)

При публикуване и при отмяна задачата `events.notify` (pg-boss) пише известие в таблото на всеки Premium Student, чийто установен учител (`verified` или `in_arbitration`) е организаторът или инструктор на събитието; известието за отмяна — само до онези, които са получили това за публикуването, и не за минало събитие. Имейл не се праща. Работникът (`pnpm worker`) трябва да върви; ако известия не пристигат, вижте **Waiting jobs** и **Failed jobs** в `/admin/system` (раздел 18) за опашката `events.notify` (лога казва само id на събитието и броеве).

Петият раздел сменя обвивката на всички екрани, затова визуалните еталони се приемат само от CI (раздел 10).

## 24. Известия за жизнения цикъл (M18)

Всяко известие на приложението минава през `notify()` (`src/server/services/notify.ts`): в таблото винаги, по имейл според каталога (`src/server/templates/catalog.ts`) и избора на акаунта. Решенията и причините са в [ADR 0021](../adr/0021-notices.md); отворените въпроси с решенията по подразбиране — в `docs/plan/questions/M18.md`.

### Данни

- `notification.dedupe_key` с уникалния индекс `notification_dedupe_key`: едно известие на акаунт и ключ (например `plan.expiring:<id на гранта>`); повторно пускане на задача не праща нищо второ.
- Таблица `notification_preference` (`docs/data-model.md`): изборът за имейл по категория и версията му. Без ред важи подразбирането (DEFAULT M18, въпрос 1): включено за `security`, `account`, `plan`, `teaching`, `review`, `schools`, `organizations`; изключено за `events`. `security` и `account` не се изключват (ограничение в базата и отказ в услугата).
- Блокиран (`banned`) или изтрит акаунт не получава нищо.

### Имейлите

- Общото писмо `notice` носи текста на известието; видовете със собствено писмо (заявките на M09, решенията на M10a–M10b) го запазват.
- Бюджет (DEFAULT M18, въпрос 7): до 20 писма от един шаблон до един акаунт за час; над него известието остава, а в лога пише `[notify] <вид> to account <id>: e-mail dropped, the hourly budget of the account is spent`.
- Писмата от категория, която може да се изключи, имат връзка за отписване и заглавките `List-Unsubscribe` и `List-Unsubscribe-Post` (RFC 8058). Токенът е HMAC с ключ, изведен от `MAIL_SEAL_KEY`: смяна на `MAIL_SEAL_KEY` прави всички стари връзки невалидни (страницата казва „This link no longer works“). Връзката важи, докато акаунтът не промени избора си. Mailpit (`http://localhost:8025`) показва заглавките на всяко писмо.
- Отписване през API: `GET /api/v1/notifications/unsubscribe?token=…` (какво би изключило) и `POST /api/v1/notifications/unsubscribe` с `{ "token": "…" }`; без вход.

### Задачи

- `plans.expiry` (всеки ден в 06:41 UTC, DEFAULT M18, въпрос 7): известия `plan.expiring` (собствен грант на акаунт, който свършва до 7 дни) и `plan.expired` (свършил до 7 дни назад), по веднъж. Не за отнет грант и не когато друг грант на същия план продължава. Лог: `plans.expiry: job <id>: N ending soon, M ended`.
- `retention.purge` (DEFAULT M18, въпрос 3) трие прочетените известия след 180 дни и непрочетените след 365 (`retention.purge: deleted N old notification(s)`).
- Ако известия или писма не пристигат, вижте **Waiting jobs** и **Failed jobs** в `/admin/system` (раздел 18) за опашките `email.send`, `plans.expiry` и `events.notify`.

### Персонал и модерация (DEFAULT M18, въпрос 6)

Когато махнете събитие, профилна снимка, снимка от галерия или снимка на школа, собственикът получава известие `content.removed` с причината, която сте написали (без вашето име), и по имейл. Затова причината трябва да е разбираема за собственика. Известието при граница (DEFAULT M18, въпрос 2) е само в таблото: едно на функция и месец при отказ `quota`.

### Демо данни и проверка

## 25. Кунг Фу паспорт (M19)

Паспортът е избран от собственика на 07.11.2026 (Фаза 2: „Training passport“). Решенията и причините са в [ADR 0022](../adr/0022-passport.md); отворените въпроси с решенията по подразбиране — в `docs/plan/questions/M19.md`.

### Данни

- Пет таблици (`docs/data-model.md`, „Паспорт (M19)“): `passport_rank`, `passport_exam`, `passport_skill`, `passport_certificate` и `event_attendance`. Всеки запис има `visibility` (`private`, `public`) и `status` (`active`, `withdrawn`, `removed`); нищо не се трие (D08), `app_rw` няма `DELETE`.
- Публичното четене минава само през изгледа `v_public_passport` (`security_barrier`): активни и публични записи на публични личности, без ключ на файл, причина, поправка или акаунт. Изгледът е само за `app_rw`; `app_public_ro` не вижда паспорта.
- Кой пише (DEFAULT M19, въпрос 1): учителят с потвърдена връзка или администратор на одобрена организация за неин член. Ученикът не вписва сам; той сменя видимостта, предлага поправка и качва сертификати. Връзка в арбитраж е само за четене.
- Нивото на паспорта зависи от плана на акаунта му (`passportLevel`, матрица `2026-11-07.1`, `docs/entitlements.md`): основен за Free Student, Free Sifu и запис без акаунт, пълен за Premium Student, Professional Sifu и Federation.

### Сертификатите (DEFAULT M19, въпрос 4)

- Само JPEG, PNG и WebP до 5 MB, до 20 активни на паспорт. Обработват се като снимките от галерията (кодират се наново, без EXIF, GPS, XMP и IPTC).
- Файловете са **в частното хранилище на доказателствата** (`certificates/<48 hex>/96`, `/512`, `/full`), никога в бъкета за снимки. Отдават се само през приложението, на `GET /api/certificates/<id>/<hash>/<размер>.webp`, никога с presigned адрес: частен сертификат само на собственика и учителите му (`Cache-Control: private, no-store`), публичен, който профилът показва, на всички (`public, no-cache`), а за всички останали — същият 404.
- Ако архивирате или възстановявате хранилището на доказателствата (раздел 18), сертификатите са в него.

### Персонал и модерация

Модератор или администратор с потвърден втори фактор вижда на профила, в раздела **Training passport**, част **Moderation**: избира запис (**Entry**), пише причина (**Reason**) и натиска **Remove the entry** (процедурата `passport.remove`). Записът става `removed` и не се показва никому, причината е в одита, а собственикът получава известие `content.removed` с нея (без вашето име). Файловете на махнат сертификат се трият. Одитът пази и `passport.add`, `passport.update`, `passport.withdraw`, `passport.visibility`, `passport.correction`, `passport.attendance`, `passport.certificate_upload` и `passport.certificate_remove`, само с идентификатори, без имена или текст на записа. В лога има само идентификатори.

## 26. Проверка за активност на школите (M20)

Пинът на школа на картата трябва да показва школа, която работи (спецификация §7.3). Решенията и причините са в [ADR 0023](../adr/0023-school-activity.md); отворените въпроси с решенията по подразбиране — в `docs/plan/questions/M20.md`.

### Етапите (DEFAULT D17)

- Всяка обявена школа (`status = 'active'`, неизтрита, обявена от акаунт) има записан етап `school.activity_stage`: `current`, `awaiting_confirmation` или `hidden`, с датите `activity_awaiting_since` и `activity_hidden_at` (`docs/data-model.md`).
- **Ден 90** без редакция или потвърждение: етапът става `awaiting_confirmation`. Собственикът получава известие `school.activity-awaiting` („Is your school listing still current?“) с датата на последната активност и ориентировъчна дата. Администраторите на организациите с приета връзка към школата получават същото известие само за сведение. Школата остава на картата.
- **Ден 105**, и никога по-рано от 14 дни след молбата: етапът става `hidden`. Пинът и обявата изчезват от картата, списъка, търсенето, страницата на школата, sitemap, Open Graph, JSON-LD и страниците на организации и събития, защото публичният изглед `v_public_school` вече не я връща. Нищо не се трие. Собственикът получава `school.activity-hidden` („Your school listing is not shown for now“) с указание как да я покаже отново.
- Активност е само редакция с истинска промяна (`schools.update`), изпращане за преглед (`schools.submit`) или **This listing is current** (`schools.confirm`). Влизането в профила не е активност.
- Връщане (DEFAULT D18): потвърждението или редакцията връщат етапа `current`. Пинът се показва отново само ако обявата е активна и одобрена, а акаунтът има Professional Sifu. На Free Sifu потвърждението се записва, но пин не се показва.
- Школите без акаунт (записи на платформата) не се проверяват.
- И двете известия са в категория **Schools**: имейлът е включен по подразбиране и собственикът може да го изключи (раздел 24).

### Задачата

`schools.activity` се пуска всеки ден в 05:23 UTC (pg-boss). Възрастта се мери с часовника на базата. Всяка школа се мести в отделна транзакция с условие, което повтаря всички проверки, така че потвърждение, записано преди това, печели. Ключът на известието е по школа, етап и период без активност, затова повторно пускане, повторен опит или две задачи наведнъж не пращат нищо второ. Пропуснати дни не скриват школа без молба. След скриване задачата изчиства публичния кеш `schools` през вътрешния адрес `/api/internal/revalidate`. Лог: `schools.activity: job <id>: N awaiting confirmation, N hidden, N notice(s)`, само броеве и идентификатори. Одитът записва `school.activity_awaiting` и `school.activity_hidden` (роля `system`). Ако задачата не върви, вижте опашката `schools.activity` в **Waiting jobs** и **Failed jobs** на `/admin/system` (раздел 18).

### Екранът на персонала

`/admin/schools` (**School activity**, връзка от `/admin`) е за модератор и администратор с потвърден втори фактор (процедура `schools.adminList`, `GET /api/v1/admin/schools`). Показва обявените школи, най-дълго неактивните първи: името, града, датата на последната активност, етапа с текст и знак, датите на молбата и на скриването и дали школата е на публичната карта. Филтърът **All listed**, **Current**, **Awaiting confirmation**, **Hidden from the map** е от обикновени връзки (`?stage=…`) с броя до всяка. Показват се до 200 школи. Няма контакти и точни координати. Персоналът не скрива и не показва школа от този екран: ръчното скриване остава модерацията на обявата (раздел 17).
