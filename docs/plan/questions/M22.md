# M22 — questions for the owner

M22 did not stop on these questions. Each one keeps its proposed default until the owner answers it. The defaults are marked in the code and the docs (`DEFAULT M22`, with the question's number, and docs/adr/0025-billing.md).

## 2026-11-11 — M22 — 1. The payment provider, and how the app talks to it

**Question:** Which provider takes the test payments, and does the app add the provider's SDK?

**Options:**
1. **Two providers behind one interface (`src/server/billing/types.ts`). The default is a local test provider (`BILLING_PROVIDER` unset or `test`): its checkout is a page of the app, it keeps its own side of each subscription, and it signs its events with an HMAC key, so CI and every local run need no account, no key and no network. The second is Stripe in test mode (`BILLING_PROVIDER=stripe`), reached with plain `fetch` on Stripe's REST API and the Stripe-Signature check written by hand (no `stripe` package, no new dependency). Only a test key (`sk_test_…`) is accepted: a live key, a restricted key or anything else stops the web process and the worker at start, and the adapter refuses any event whose `livemode` is not false. The Stripe adapter is never called in CI; its unit tests use recorded, fictional payloads and a fake fetch.**
2. Stripe only, through its official SDK (a new dependency, and a Stripe account for every run, CI included).
3. The test provider only; Stripe later.

**Proposed default:** option 1, applied (`src/server/billing/config.ts`, `stripe.ts`, `test-provider.ts`). A real charge needs a separate decision and a separate milestone (D09 and plan §3.3: no paid resources).

## 2026-11-11 — M22 — 2. A declined test card

**Question:** What does a declined card leave behind?

**Options:**
1. **Nothing: no customer, no subscription, no event. The checkout stays open on the test checkout page with "The test card was declined", and the payer can choose another test card. This is how Stripe Checkout behaves: a declined card never completes the session.**
2. A subscription in the state `incomplete`, shown on the billing page.

**Proposed default:** option 1, applied (`testPay` in `src/server/services/billing.ts`; the test provider's `pay`). The `incomplete` status exists for a Stripe subscription that is created before its first payment and is never shown as a plan.

## 2026-11-11 — M22 — 5. A failed renewal

**Question:** What happens when a renewal payment fails?

**Options:**
1. **The subscription becomes `past_due` ("Payment failed", with a shape as well as words). The plan stays for a grace period of 7 days from the failure (`BILLING_GRACE_DAYS`); the account is told when it fails and when it recovers. The hourly job `billing.grace` ends a subscription whose grace has run out: it cancels it at the provider, ends the plan grant and tells the account ("the plan has ended; nothing you added is deleted"). A downgrade keeps every record (D08, D06): links stay confirmed, a pin is hidden, never deleted.**
2. No grace: the plan ends at the failure.
3. A longer grace (14 days), or the provider's own retry schedule only.

**Proposed default:** option 1, applied (`accessUntil`, `endExpiredGrace` in `src/server/services/billing.ts`; `src/server/jobs/billing.ts`).

**Answer:** (filled in by the owner)

## 2026-11-11 — M22 — 6. The billing notices

**Question:** Can the notices of a subscription be switched off?

**Options:**
1. **No. They are a category of their own, `billing`, locked like security and account notices: they say what happens to a payment and to access, so they are always in the dashboard and always e-mailed. Six notices: started, cancel scheduled, resumed, payment failed, payment recovered, ended. Each says "This is test mode: no real charge is ever made." The plan-ending notices of M18 cover a paid plan only when it was cancelled (a renewing subscription has no "end").**
2. In the existing `plan` category, which can be switched off by e-mail.

**Proposed default:** option 1, applied (`src/server/templates/catalog.ts`, `LOCKED_NOTIFICATION_CATEGORIES`).

**Answer:** (filled in by the owner)

## 2026-11-11 — M22 — 7. Open checkouts

**Question:** How long does a checkout stay open, and how many?

**Options:**
1. **An hour (`CHECKOUT_TTL_MINUTES`), and one per account: a new checkout replaces the open one (it becomes `expired`). A checkout is refused while the account has a live subscription (active or past due). Stripe's own session expiry is set to the same hour.**
2. 24 hours (Stripe's default), several at a time.

**Proposed default:** option 1, applied (`startCheckout`).

**Answer:** (filled in by the owner)

## 2026-11-11 — M22 — 8. The account type while a subscription renews

**Question:** Can an account switch between Student and Sifu while it pays for a plan of its type?

**Options:**
1. **Not while the subscription renews: the switch is refused with "cancel the subscription first" (409). After a cancellation at the period end it is allowed, and the paid plan of the old type simply runs out at the period end. A switch expires the account's open checkouts.**
2. Allowed, and the subscription is cancelled at once (with or without a refund).

**Proposed default:** option 1, applied (`beforeAccountTypeChange` in `src/server/services/billing.ts`, called by `changeAccountType`).
